# 代理 IP 与密钥轮换约束

## 客户端 IP

`App.TrustLoopbackProxy=false` 是默认值；应用直接使用 TCP 对端地址，不接受客户端自行提供的 `X-Forwarded-For`。

仅在同机反向代理隔离应用端口、且代理**覆盖** `X-Forwarded-For` 为一个规范 IP 地址时启用 `TrustLoopbackProxy=true`。不要让互联网客户端直接访问受信任的回环代理入口，也不要将外部传入的 XFF 原样透传。当前 `ClientIp.Resolve` 只信任回环对端的单个地址，含多个地址、无效值或非回环对端均回退到对端地址。

这是一跳部署契约。ARR/CDN 多跳链路不在当前可信代理配置内：上线前必须核对代理地址及各跳覆盖/追加行为，并由最靠近应用的受信代理产出规范单 IP。不要在应用里直接信任 XFF 第一项；它可能由客户端伪造。限流回退到代理地址会合并客户端配额，应以实际链路的请求证据验证 IP 解析后再放量。

## JWT 与 SMTP 密钥轮换

当前数据库中的 SMTP 密码密文使用由 `JwtSecret` 派生的密钥。轮换 JWT 密钥会同时使现有 access/media token 失效，并使旧 SMTP 密码无法解密；它不会自动重新加密数据库里的密码。

计划轮换时应先准备受保护的新配置及可恢复备份，在停站维护窗口更换密钥，启动后重新登录并在邮件配置中重新输入 SMTP 密码，验证 `PasswordNeedsUpdate=false` 和邮件测试投递成功。不要仅检查 `/health` 就宣布邮件恢复，也不要将密钥或 SMTP 密码写入审计报告。

若需要独立轮换，应另行迁移到独立数据保护密钥并提供旧密文迁移路径；直接修改派生算法会让全部已有密码失效。

## 保留的身份策略

连续登录失败后的账号锁定和无角色账号可由拥有用户管理权限的内部人员维护，均保留当前业务行为。权限委派上限仍在有角色目标上执行；供应商角色中的专属权限按既有可委派集合处理。更改账号锁定为渐进延迟、或要求无角色目标仅由系统管理员管理，会改变业务权限与解锁流程，应作为明确的策略变更交付。

## 时间戳

所有应用数据库连接（原生请求、EF 自有连接、初始化）在打开后设置 `time_zone='+00:00'`，因此 `CURRENT_TIMESTAMP`、自动更新时间与 UTC 读取一致。该修复不推测或批量纠正已存历史时间：只有知道写入时服务器时区、连接来源和字段写入方式后才能制定历史数据修复方案。
