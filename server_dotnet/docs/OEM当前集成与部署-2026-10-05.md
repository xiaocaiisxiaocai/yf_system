# OEM 当前集成与部署（2026-10-05）

本文描述当前 .NET 8 实现和发布方式，是 OEM 运行、配置与部署的现行入口。2026-09-18 的需求、数据库/接口规划及 2026-09-19 的审查记录保留为设计与修复历史；字段、命令和运行边界以当前源码、迁移、`deploy/appsettings.example.json` 与本文为准。

## 当前范围

OEM 已恢复为独立业务线，包含公司到 OEM、OEM 到公司的双向传递，分片上传，审批，文件格式与归档结构检查，安全发布/下载，删除策略，存储核对，邮件通知与审计。OEM 身份、权限、传递单和文件状态保存在同一业务数据库；文件字节只进入 `App:OemStorageRoot`，不得进入协作文件的 `App:StorageRoot` 或共享 blob。应用不提供内置病毒库或恶意软件扫描，格式/结构检查不构成杀毒结论。

`OemStorageRoot` 的固定布局为 `uploads/`、`quarantine/` 和 `available/`。隔离区与可用区必须在同一卷，检查完成后的发布使用原子移动。该根目录必须是本地绝对非盘根路径，并与程序目录、协作存储、配置、日志、发布包和备份目录双向不重叠，不得经过 junction 或 symlink（安装时由 `install-iis.ps1` 核对前五类；备份目录只在 `maintain-iis.ps1` 的 Backup/Upgrade/Restore 中核对）。

普通协作部署无需启用 OEM。模板默认 `OemStorageRoot=""`：API 和协作业务可以启动，OEM 文件入口会明确返回未配置。配置 OEM 时只需提供独立的本地存储根；部署脚本会继续校验路径隔离、ACL 和恢复后的存储核对。

内部入口为 `/oem`，厂商独立门户为 `/oem-portal`。内部员工复用现有身份缓存和会话即时撤销；供应商账号不能进入 OEM，OEM 令牌不能访问协作平台。OEM 刷新会话继承固定绝对截止时间，并使用现有 `AbsoluteSessionLifetimeDays`、`MaxActiveSessionsPerUser` 配置；轮换不能延长会话族寿命。

厂商来件通知（2026-11-12，取代“OEM → 公司发给全部具备 OEM 查看和下载权限的启用内部员工”）：具备 `oem:transfer_view` 与 `oem:file_download` 的启用内部员工默认都在每个厂商的“可通知人员”名单中，新建或导入的员工获得权限后自动加入。管理员（`oem:company_manage`）在“厂商与账号”页可把人从全部厂商一次移除（`oem_internal_recipient_exclusions`，`GET /oem/internal-recipients`、`PUT /oem/internal-recipients/{userId}`），或只从某个厂商移除（`oem_company_recipient_exclusions`，`GET /oem/companies/{id}/internal-recipients`、`PUT /oem/companies/{id}/internal-recipients/{userId}`），请求体 `{ removed }`，移除后可恢复。厂商发送文件时从名单中勾选本次要通知的人（`GET /oem/transfer-recipient-choices` 仅向该厂商账号返回有邮箱者的姓名，不含工号；`POST /oem/transfers/{id}/send` 的 `recipientUserIds`），名单中有人时至少选一人且只能选名单内的人；名单为空时可直接发送但不发邮件。所选人员保存在 `oem_transfer_internal_recipients`，发布邮件只发给这些人，投递前复核其仍被选中且仍在该厂商名单中（未被移除、仍有查看和下载权限）；没有可通知的人时记 `OEM_EMAIL_SKIPPED_NO_INTERNAL_RECIPIENT`。公司发出的传递单不接受 `recipientUserIds`（400）。

传递单可见范围（2026-11-12，取代“具备 `oem:transfer_view` 的内部人员可查看全部非草稿传递单”）：只有内置“系统管理员”角色（且具备 `oem:transfer_view`）可查看全部传递单。其他内部人员只看到自己发出的、自己参与审批的（审批任务规则不变）以及厂商发送时勾选通知自己的来件；组织负责人（`departments.leader_account_id`，且具备 `oem:transfer_view`）另可看到其所负责组织及全部下级组织当前成员发出的外发单，以及厂商勾选通知了这些成员的来件，内容读取规则与管理员相同（需 `oem:file_download`）；列表、详情、预览和下载按同一规则（`TransferAccess`），看不到的单详情返回 404。公司出站已发布内容的“查看+下载可读”同样仅限管理员；审批阻断处置中“兼具查看与异常处置权限”的完整处置范围也仅限管理员。

厂商来件签名（2026-11-12）：与 Robot 供应商上传一致，厂商共用账号发送 OEM → 公司传递单时须填写签名（提供人姓名，最多 32 字），必须与该厂商某个启用联络人的姓名一致（大小写／全半角不敏感，保存登记写法）；厂商没有启用联络人时可不签名。签名保存在 `oem_transfers.signer_contact_id` / `signer_name`，摘要返回 `signerName`，界面发送人显示为“签名（登录账号）”，发送人筛选也匹配签名；公司发出的传递单不接受签名（400）。发送审计记录 `signerName`。

内部文件传递单列表支持 `departmentId` 组织筛选（2026-11-11）：按内部发送人**当前所属组织**匹配，包含选中事业部／部门／课别及全部下级，停用组织仍可用于历史查询。无内部发送人的 OEM 回传单不匹配；未知组织返回空列表，非法或零编号返回 400。该条件与厂商、发送人、方向、状态、时间、本人及最新／历史条件取交集，不扩大原有可见范围。厂商门户不提供组织筛选，携带该参数返回 403。

事业部、部门和课别主管统一在协作平台的“组织架构”（`/org/depts`）维护，使用现有 `dept:leader_manage` 权限。OEM 不再提供独立主管配置页；旧 `/oem/admin/leaders` 地址重定向至组织架构。两条业务线使用同一组织主管数据；设置主管不会自动授予 OEM 审批权限，已发起审批保留原审批人。自 2026-11-05 起：一人只能担任一个组织的主管；主管必须属于其所管组织或该组织的下级组织（候选列表只列出这些人员）；调整账号所属组织或移动组织后若违反上述规则，操作被拒绝，需先更换主管。

审批模板的主管类节点只有一种来源「上级主管」（`DIRECT_LEADER`，2026-11-05 起取代课别／部门／事业部主管三种来源），每个模板最多一个，可与指定人员节点组合。发送人可归属任意层级的已启用组织；上级主管取发送人所在组织的主管，该组织未配置主管时，沿上级组织逐级找最近一个配置了主管的组织；遇到停用组织即停止。整条链都没有主管时不能发送。2026-11-05 起以下发送人**整张传递单免审批**（模板所有节点，包括指定人员节点，都记为免审，审批实例为 `SKIPPED`，文件校验通过后直接放行）：发送人本人是其组织链上任一组织（课别／部门／事业部）的主管（`skipReason=INITIATOR_IS_LEADER`，此前为向上升级）；发送人直接归属部门或事业部、不在任何课别下（`skipReason=ABOVE_SECTION`，此前由部门／事业部主管审批）。因此上级主管节点不再使用“发起人即审批人”策略和备用审批人，保存模板时统一规范为 `SKIP`；指定人员节点的该策略仍适用于课别内的普通员工。找到的主管停用或没有 `oem:flow_approve` 时报错，不再向上越级。迁移 `MergeOemLeaderApproverSources` 把每个模板的第一个启用的分级主管节点（都未启用时取第一个）改为上级主管，删除其余分级主管节点；已发起的审批保留原来源与审批人。

同一审批人可出现在多个节点（2026-11-05 起，取代 V0.5“同一人出现在多个节点即配置错误、发送失败”的规则）：节点激活时，若某审批人已在本实例的前序节点审批通过，其任务自动通过（原因“已在前序节点审批通过，自动通过”，审计 `OEM_APPROVAL_AUTO_APPROVE`）；或签节点因此直接通过，会签节点只剩其他审批人待审，全部自动通过时该节点直接通过并继续下一节点。前序节点只是候选但未亲自审批（例如或签由他人通过）时不算。

发送入口统一为“发送文件”：内部员工选择 OEM 厂商、拖入或选择文件后直接提交审批，前端连续完成草稿创建、分片上传与提交，无需先填标题或另进详情页发送。标题由文件名自动生成；审批及文件校验完成后自动向 OEM 放行。OEM 回传沿用原有规则，上传并提交后在文件校验完成时自动送达内部，不新增内部外发审批。失败时保留草稿与已完成的上传，重试前核对服务端状态，避免重复提交。

内部向 OEM 发送时，目标厂商须已启用且至少有一个启用的 OEM 登录账号。无账号或账号全部停用的厂商在选择列表中不可选并显示原因；服务端在创建草稿及提交审批时都重新检查，不能绕过前端限制。仅有空草稿的厂商允许停用或删除最后一个启用账号，存在传递业务历史的启用厂商仍须保留接收账号。厂商停用期间账号被停用/删除后重新启用，也可能没有启用账号；此时提交失败并保留草稿和文件，不启动审批；新增或启用账号后可继续提交。其他厂商的账号不能满足该条件，首次登录须改密和临时登录锁定不视为账号停用。

管理员在“统一删除策略”中维护一项当前规则，发送页面不再要求选择策略，服务端也不接受发送人用模板 ID 覆盖统一规则。旧版本存在多个启用模板时，编号最小的启用项作为唯一生效项，管理员保存规则后将其他启用项停用，历史模板保留。策略在提交审批/发送时冻结，后续调整只影响新提交的文件，不改动已提交记录的快照与删除期限。

厂商和登录账号同时支持停用与删除。删除分别要求管理权限及 `oem:company_delete`、`oem:account_delete` 专用权限；升级只自动授予内置系统管理员，其他角色按需分配。厂商须先删除关联账号。账号和厂商的删除检查按下面的规则区分空草稿与业务历史。仅登录、登录失败、退出及改密日志不阻止删除，日志及账号名称快照继续保留。存在业务引用时拒绝删除并提示停用，不级联删除历史；无引用账号删除时清理刷新会话，删除审计保留名称和工号快照。

空草稿指未发送、未发布且未冻结文件清单的 DRAFT 或 ABANDONED 传递单，须同时没有文件行（含已移除或已清理的附件）、上传会话、审批实例和邮件通知记录。该规则也适用于已有数据。管理员列表可能看不到他人草稿，删除检查仍按账号所属厂商 ID 核对，只有具备业务历史的传递单才触发最后启用账号保护。停用账号不清理草稿。

删除账号时，仅清理该厂商下由该账号创建或关闭的空草稿。上述草稿的创建、编辑、废弃审计保留原记录，不阻止删除。其他人员发给该厂商的空草稿继续保留，到删除厂商时才清理。删除审计记录本次清理的空草稿数。权限复核、业务历史检查、草稿清理和目录删除在同一排他管理事务内完成，与草稿创建、上传和发送串行。

登录账号不区分大小写，保留创建时拼写；创建、导入和登录使用相同身份。例如 `ABC` 和 `abc` 不能作为两个 OEM 账号。ODM/OEMA 所有厂商共用一个账号名称范围，与 Robot/内部账号的名称范围分开；Robot 厂商与内部员工账号不可重名。密码仍区分大小写。

厂商存在任一方向的进行中传递单（已发送 `SEALED`，尚未发布、驳回、阻断或终止）时不能停用，返回 409/40901 并提示数量，管理员须先终止或等待其完成；草稿不计入。删除厂商仍要求无账号且无传递业务历史。

审批参与者可凭审批权限访问自己的任务详情。只有 `oem:approval_recover`、没有 `oem:transfer_view` 的异常处置角色使用“审批阻断处置”入口，仅可处理外发、已密封且 `APPROVAL_BLOCKED` 的传递；详情不返回附件、描述或 manifest，成功改派或终止后返回恢复列表。兼具查看与异常处置权限的管理员保留原有未发布单处置能力；版本、原因、合格审批人及禁止代审规则仍在事务内校验：新审批人不能是发送人或执行改派的本人；流程处于 `APPROVAL_BLOCKED` 时可改派回已恢复资格的原审批人。（2026-10-31）

外发传递审批通过后、发布前，服务端在传递单行锁内再次检查收件条件（与创建草稿、提交审批相同：厂商为启用状态且至少有一个启用账号）。审批期间厂商被停用或账号被全部停用/删除时不发布，传递单转为 `BLOCKED`，原因记为“收件厂商已停用或没有可用账号，未发布”，写入 `OEM_TRANSFER_BLOCK` 审计、通知发送人并按阻断保留期清理附件；与发布前附件不可用的处理方式一致。需要继续传递时，恢复厂商账号后重新发送新的传递单。

版本不匹配（调用方提交的 `version` 与当前行不一致）返回 `409 / 40903`“数据已被他人修改，请刷新后重试”。名称已存在、状态机不允许、配额、仍有附件正在上传、任务已处理等其他 OEM 冲突仍为 `409 / 40901`。前端遇到 40903 时重新读取聚合，并保留已填写的原因或标题（2026-10-22）。

待审批列表 `GET /api/v1/oem/approvals/pending` 为分页接口（`page`、`pageSize`，返回 `list/total/page/pageSize`），按任务进入待审批的时间 `activatedAt` 及任务 ID 升序稳定排序。`oem_flow_tasks.activated_at` 在节点激活（含首个节点和流转到下一节点）及改派生成新的待审批任务时写入；迁移 `AddOemApprovalTaskActivatedAt` 为已存在的待审批任务按改派创建时间、上一节点完成时间或审批实例最后更新时间回填。

OEM 邮件在实际发送前重新检查厂商、账号、业务状态及当前邮箱；收件地址已变化时取消排队邮件。OEM 邮件以 `INSERT IGNORE` 按 `email_outbox.dedupe_key`（如 `oem:approval:{taskId}`、`oem:released:{transferId}:{realm}:{accountId}`）幂等入队；被取消（规则关闭、收件人失效、业务状态变化等）的 OEM 行保留其 `dedupe_key`，因此同一通知键之后不会重新入队或补发，即使重新打开开关或恢复收件人也一样。只有协作的合并类事件（`FILE_UPLOADED`、`MESSAGE_CREATED`）在发送/取消时清空键。已结束行在 `App:MailRetentionDays`（默认 90 天）后被清理，此后键才会释放。孤立文件清理拒绝根或任何祖先目录重解析点，内容区发现链接时整区不删，删除前再次核验路径，避免影响协作存储。

数据库通过新增 `RestoreOemPlatform` 向前恢复 19 张 OEM 表及必要共享字段；原 `AddOemPlatform`、`DropOemPlatform` 和当前协作结构均保留。新增表结构不恢复此前删除的数据，历史数据恢复需要对应备份。

从带有旧扫描状态的版本升级时，先用 `maintain-iis.ps1 -Action Upgrade` 完成数据库的可验证离线备份（OEM 文件根按设计不备份，迁移也不改动其中的文件；回退时用 `-Action Restore -ReuseOemStorage` 沿用同一根），再按迁移历史显式执行 `20261006031500_ReplaceOemMalwareScanningWithValidation`。该迁移保留旧 scan 物理列/表作为历史兼容，把新校验状态写为 `VALID`、`INVALID` 或 `WAITING_FILES`，重置未完成的待处理任务，并将 `oem.scan.*` 文件规则迁移到 `oem.validation.*` 后移除病毒库配置。`VALID` 只表示文件完整性、格式和归档结构校验通过，不能解释为病毒扫描结果或 `CLEAN`；已有阻断状态不会因此放行。若需要降级，必须同时恢复与备份匹配的旧应用和数据库，不能用新校验字段伪造旧扫描结论。

## 启用生产 OEM

在网站外部私有配置中补充独立存储根：

```json
{
  "App": {
    "OemStorageRoot": "E:\\YfOemData"
  }
}
```

创建 `OemStorageRoot` 后给应用池身份修改权限。`install-iis.ps1` 会核对它与发布包、站点程序目录、外部配置、协作存储和日志目录双向不重叠，并设置受限 ACL（安装脚本没有备份目录参数，不核对备份目录）；`maintain-iis.ps1` 在 Backup/Upgrade/Restore 时把 OEM 根纳入路径隔离，拒绝 `-BackupDirectory` 位于其中或包含它；升级沿用既有根并补充应用池权限（新启用 OEM 时目录必须已存在，脚本在停池前检查）；恢复默认要求新的空根，`-ReuseOemStorage` 时沿用当前根。当前 IIS 单进程约束同时适用于 OEM worker：同一数据库和 OEM 根不能由第二个站点、服务或服务器副本并发处理。

上传内容仍会执行普通文件格式和归档结构检查，包括 SharpCompress 支持的归档格式、条目数量/深度和展开预算约束。ZIP 在打开前先流式统计中央目录记录数，超过条目上限直接拒绝，不把整个目录读入内存。归档内条目同样拒绝可执行程序（MZ/ELF/Mach-O/脚本头），并拒绝含 `..`、绝对路径或盘符的条目名。非归档文件（含归档内的非归档条目）若在末尾 64 KiB 搜索窗口内带有指向其前方中央目录的 ZIP 结束记录（与解压工具一样容忍其后的尾部字节）、或在前 1 MiB 内（偏移非 0）含 RAR/7z 签名，视为夹带压缩包并拒绝，防止前置或尾部字节绕过加密与展开检查。docx/xlsx/pptx 只允许 `*/embeddings/` 下的一层内嵌包（如图表的工作簿），按普通归档继续检查；其他位置的嵌套归档、以及扩展名为 docx/xlsx/pptx 的 OLE2（加密 Office）条目均拒绝。条目实际读取量超过记录大小即判损坏；归档整体压缩比按已声明大小在解压每个条目前累计检查（7z 没有单条目压缩大小）。校验超时（15 分钟 + 每 GiB 2 分钟）与解析标头时内存不足同样直接判 `INVALID`，不再重试占用单一校验队列。归档解析器抛出的任何异常都按内容损坏判定为 `INVALID`；只有校验工作目录写入失败等环境问题按可重试错误处理，并计入 `oem.validation.max_retries`。该检查用于限制结构风险，不提供恶意软件扫描或病毒库结论。



## 备份、恢复与验收边界

EF 的同步、异步迁移及 `dotnet ef` 入口会在执行任何迁移前检查完整回滚路径。若路径包含 `ReplaceOemMalwareScanningWithValidation` 等拒绝 `Down` 的迁移，整次回滚立即拒绝，后续较新的迁移也不会先被撤销，迁移历史、自定义角色授权和业务字段保持原样。仅回退到该迁移本身、未跨越不可回滚边界的操作仍按原 `Down` 执行，可能删除权限或字段数据；生产降级继续使用匹配的应用与数据库备份恢复，不能把可执行 `Down` 理解成数据无损。

IIS 维护备份包含数据库、程序、外部配置和协作 `StorageRoot`，故意不复制 OEM 文件根。备份脚本把 `OemStorageRoot` 纳入路径隔离，避免备份目录误落入其中。Restore 默认使用新的空 OEM 根，并在导入数据库后设置 `oem.storage.reconcile_required=RESTORED`（脚本回读确认标记已写入）；此时历史文件在核对后永久为 `MISSING_UNVERIFIED`。`-ReuseOemStorage` 沿用当前根（例如迁移失败回退），核对会保留仍在盘上的文件，并把备份后才晋升到 `available/` 的同名文件经大小与 SHA-256 核对后移回记录位置。核对期间上传初始化、分片写入、合并、发送和文件读取都返回 503（50302）。手工恢复数据库而沿用 OEM 根时，启动前执行 `dotnet .\Yf.Api.dll --oem-mark-restored`。OEM 在线文件若需要灾难恢复，应由组织另行定义加密介质、保留期和与数据库一致性点，不能把协作备份误称为 OEM 文件备份。

交付证据分层记录：源码/脚本检查、发布目录或 ZIP 内容、目标 IIS 安装、独立 OEM 存储 ACL 与恢复核对、SMTP 收件、业务全流程分别验收。开发机打包或静态检查不能证明目标 IIS、邮件或生产业务已经可用。

## 校验、下载与存储补充（2026-11-01）

- 压缩包条目名拒绝冒号、规范化后重名、段尾点或空格、Windows 保留设备名（包括 `con.txt`）以及符号链接/硬链接。OEM 上传文件名拒绝 Unicode `Cf` 格式字符。
- 校验任务按厂商轮转，每轮优先各厂商最早的未完成任务；每家厂商最多排入 100 个未完成的校验任务。预览、下载发起和上传初始化分别按账号限流：预览每分钟 120 次，下载发起与上传初始化各 60 次（与 Robot 协作一致），超限返回 `429 / 42902`。
- 收取上传分片时先写入临时文件。替换已确认分片前，服务在持有业务授权锁的事务内复核登录会话、账号、厂商状态和内部发送权限。传输途中退出或被撤权会被拒绝，服务删除本次临时文件并保留之前确认的分片。
- 终态 OEM 上传会话保留 7 天后清理。下载流每 5 秒心跳复核账号和下载会话；实际计入下载进度的字节以成功 flush 到响应流的字节数为准，至少每 1 MiB 或每 5 秒 flush 并确认。
- 存储核对在根不可读或缺失比例异常时跳过整批并告警 `OEM_RECONCILE_STORAGE_SUSPECT`，不把卷未挂载误判成文件丢失。超过 5 个且占本批文件一半以上同时缺失会触发批次熔断。之后若 `STORAGE_LOST` 文件在记录的 `available/` 或 `quarantine/` 路径重新出现，且大小与 SHA-256 均匹配，对账会恢复为 `AVAILABLE` 或 `QUARANTINED`，写 `OEM_FILE_STORAGE_RESTORED`（只记录路径类别），并按既有保留策略补清理期限。**传递单仍保持终态**：丢失曾使其变为 `BLOCKED` 并取消开放审批；现有“审批阻断处置”只处理 `SEALED + APPROVAL_BLOCKED`，不会重开这个 `BLOCKED` 传递单。找回文件只恢复载荷事实，不重新发布或恢复审批流程。
- RAR 声明窗口和 7z LZMA/LZMA2 声明字典超过 256 MiB 时拒绝。7z 字典元数据由 SharpCompress 内部结构反射读取；反射结构不可读时记录一次告警并继续常规内容校验，升级 SharpCompress 时由真实 7z 守护测试检查该访问路径。
- 页内预览（2026-11-10）：PDF、图片（PNG/JPG/GIF/WebP/BMP）、Excel（xls/xlsx/xlsm/xlsb）、PPTX 与 Word（docx）在 50 MiB 以内可带水印页内预览，渲染器与 Robot 协作共用，字节只经 `GET /oem/files/{id}/content` 读取。旧版 `.doc`/`.ppt`、TIF/PSD/AI、CAD、压缩包等其余格式浏览器无法渲染，不提供预览；凡有内容读取权的人（发送人、当前待审批人、接收方）都可下载，审批人下载记为 `REVIEW`，不计入接收回执。
- 列表直接下载（2026-11-10）：传递单列表每行返回 `downloadableCount`，与详情的 `downloadable` 同一判定（内容读取权 + 校验通过 + 可用 + 未到删除时间）。大于 0 时最后一列显示“预览”和“下载”：点击先读详情复核，单个文件直接预览或下载（不支持预览的格式提示下载查看），多个文件弹出文件清单逐个预览或下载，不进入详情页；列表数量过期时提示不可下载并刷新列表。
- 公司出站内容读取（2026-11-10，取代“发布后仅具备查看+下载权限的实际发送人可读”）：审批中（SEALED）仅实际发送人与审批人（当前待审及之前节点已审）可预览下载，其他内部人员只看元数据；发布后（RELEASED）实际发送人、该单所有已审批人、具备 `oem:transfer_view` + `oem:file_download` 的内部人员均可预览下载，便于事后核查外发内容。审批人读取记为 `REVIEW`，其余记为 `SENDER`，都不计入厂商接收回执；被驳回、阻断、终止或放弃的传递单仍不可读取内容。
- 文件下载流也会周期性复核登录账号及下载会话。厂商视角的公司发送人不返回内部工号，统一把已完成审批状态显示为“已通过”。
- 存储迁移删除阶段先删除旧根中已核验的文件，再清理旧根空目录；不会递归删除新根或旧根中的非系统内容。
