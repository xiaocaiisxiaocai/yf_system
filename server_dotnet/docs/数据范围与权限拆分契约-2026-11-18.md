# 数据范围与权限拆分契约（2026-11-18）

动作权限回答"这个账号能做什么"，数据范围回答"它能看谁的项目和传递单"。两者互相独立：扩大范围不需要新权限点，持有权限也不会自动看到范围外的记录。

## 1. 两个维度

| 维度 | 存储 | 取值 |
| --- | --- | --- |
| 动作权限 | `permissions` / `role_permissions` | 权限码（如 `project:update`、`oem:transfer_view`） |
| 数据范围 | `role_data_scopes` / `user_data_scopes` | `SELF` / `ORG` / `ALL`，按业务域独立 |

业务域：`project`（项目）与 `oem_transfer`（ODM/OEMA 传递单）。两个域互不影响，同一个账号可以项目 `ALL`、传递单 `SELF`。

## 2. 解析规则（`DataScopeService`）

1. 用户显式覆盖（`user_data_scopes`）优先。
2. 否则取当前启用角色的默认值（`role_data_scopes`）。
3. 否则：领导至少一个启用组织的账号回落到 `ORG`，其余 `SELF`。
4. `ORG` 的覆盖集合 = 本人所在组织 + 本人领导的组织，向下展开；停用组织不授予其自身及下级的权限。
5. 停用账号不影响历史归属：主管仍能看到这些账号经手或被通知过的传递单（`OrgUserIdsAsync` 不按账号状态过滤）。

项目侧统一走 `ProjectAccessService.VisibleQueryAsync`（列表）与 `Authorize`（详情/写入）；OEM 侧统一走 `OemTransferReader.TransferRangeAsync`。新增读接口时必须复用其中之一，不要自己拼数据范围条件。

## 3. 委派上限

非系统管理员在任何授予路径上，都不能让别人的范围看到自己看不到的记录（`DataScopeCeiling`，比较规则 `DataScopeService.Covers`）：

- `ALL` 覆盖一切；`SELF` 被任何范围覆盖；`ORG` 只被 `ALL`，或被覆盖组织集合包含它全部组织的 `ORG` 覆盖。`ORG` 按实际组织比较，不只比级别：本事业部的 `ORG` 管理员不能给另一个事业部的人 `ORG`（2026-11-18 起）。
- 每条授予路径在写入前快照操作者与受影响账号的范围，写完后在同一事务内按**写入后生效的范围**校验，不通过则整笔回滚。范围、角色、组织在同一次请求里一起变时，只有最终结果说了算（例如“换成全部范围的角色 + 清除个人覆盖”“设为 ORG + 调到子树外的组织”都会被拒绝）。
- 受影响账号：用户的新增、编辑、单独设置范围、单独更换角色——该账号；设置或清空角色默认——该角色的全部成员。
- 显式设置（包括清除覆盖）的那一域总要校验；其余域只在结果比原来宽时校验，所以收窄、不变总是允许。
- 角色默认值另外按级别校验：即使角色还没有成员，也不能设成高于自己级别的值。

系统管理员不受上限约束。系统管理员的 `oem_transfer` 范围固定为 `ALL`：查询、显示、保存三处一致，写入非 `ALL` 直接 400。

## 4. 回填策略（迁移 `AddDataScopesAndCrudPermissions`）

- 只按旧读接口**实际检查**的 manage 码回填读码：`user:manage→user:view`、`supplier:manage|supplier:account→supplier:view`、`role:manage→role:view`、`dict:manage→dict:delete`、`oem:transfer_create→oem:transfer_update|oem:transfer_delete`。
- 只持有菜单码（`org:user`、`supplier:list`、`rbac:role`）的角色不回填读码——它们升级前本来读不到列表。
- `oem:directory_view` 不自动回填：它只覆盖厂商与账号的只读视图，联系人邮箱仍由 `oem:company_manage` 控制；旧角色靠原有管理码保持原能力。
- `oem:transfer_delete` 回填给创建者，保证"上传失败后删除草稿再重试"的流程不断；该权限同时允许删除自己范围内的草稿。
- 数据范围初始值：有 `project:list` 的既有角色获得 `project=ALL`（保持升级当天的可见性），系统管理员在两个域都是 `ALL`。全新库由 `BootstrapSeedCatalog` 写入同样的两行。

## 5. 写入原子性

- 角色抽屉：`PUT /admin/roles/{id}/authorization`，`permissionIds` 与 `scopes` 任一为 `null` 表示"这部分不改"，两者在同一个事务里写入并分别落审计。
- 用户编辑与创建：`POST /admin/users`、`PUT /admin/users/{id}` 都接受可选 `scopes`，与资料/角色在同一事务内完成。
- 前端只提交实际变化的数据域，写前重新读取服务端值，冲突则要求用户重新打开表单。

## 6. 只读入口

新读码（`user:view`、`supplier:view`、`role:view`、`oem:directory_view`）同时被菜单、登录落点与路由守卫接受；只读页面按写权限隐藏编辑、停用、重置密码和导出等动作。字典删除由独立的 `dict:delete` 控制（与 `user:delete` 一样，属于"管理 + 删除"组合）。

## 7. 已知取舍

- 范围外的项目返回 `403 NotVisibleMessage`（不隐藏存在性），写入仍返回 `403 OwnerOnlyMessage`。
- 删除项目时在事务内快照受众，异步通知沿用该快照；推送只含项目编号与变更类型，客户端重新拉取时按最新权限校验。
- 实时受众在每次发布时计算一次（可见账号查询 + 必要时组织树），不做跨请求缓存：缓存需要与权限和部门变更联动，当前以正确性优先。
- 密码重置、停用、删除等敏感账号管理仍按动作权限与角色委派上限判断，不按目标账号的数据范围（业务决定）。
- 任命组织主管（`dept:leader_manage`）不受数据范围上限约束：没有个人覆盖和角色默认的主管会回落到 `ORG`，因此主管任命权本身就意味着可以给出该组织的 `ORG` 范围。持有该权限的账号应视为组织管理者（业务决定，`DepartmentLeaderTests` 固定了只持有该权限即可任命）。
- 启用、停用或移动组织会改变 `ORG` 覆盖的组织集合，这些操作按 `dept:manage` 判断，不做范围比较。
