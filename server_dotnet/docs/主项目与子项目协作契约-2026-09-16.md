# 主项目与子项目协作契约

## 数据归属

- 主项目是项目列表的顶层对象，统一维护供应商、工令号、机型、Robot 厂商与型号、负责人、课别、优先级、预计完成日期及项目说明。
- 子项目必须归属于一个主项目。`projects.project_group_id` 为非空外键，不能产生孤立子项目。
- 新建子项目时继承主项目当前公共资料；子项目只维护自己的名称和说明。
- 主项目资料更新时，未完成子项目同步业务资料和工令号；已完成子项目保留验收时的业务资料与工令号快照。
- 负责人和课别属于访问控制资料。更换主项目负责人时，所有子项目（包括已完成子项目）都同步新的负责人和课别，旧负责人立即失去由负责人身份带来的访问权。
- 文件、留言、截图、已读回执、动态、复制履历和验收状态均按子项目 ID 独立保存。主项目没有文件或留言接口。

## 公司内部与供应商的访问范围

- 供应商侧以企业为访问边界：关联供应商下所有启用账号均可查看该主项目及其子项目，不维护项目成员名单。
- 公司内部以负责人为访问边界：当前负责人可查看；拥有 `project:view_all` 的内部账号可查看全部项目。
- 创建人不会因创建行为长期获得访问权，历史负责人也不会因旧关系继续访问。
- `project_members` 和 `project:member` 已退出模型。前端不提供成员页签，后端不提供成员维护接口。
- 负责人必须是启用的内部账号，直属组织必须为课别，并且其有效角色具有 `project:list`。
- 负责人仍负责草稿或进行中的主项目时，不允许停用账号、调离课别、换成无 `project:list` 的角色，也不允许禁用或移除对应角色的 `project:list`；必须先转交项目。

## 文件和留言

- 公司与供应商都可按权限上传文件、发送留言和查看各自可见的协作内容。
- 文件方向由上传人身份确定：内部上传为 `C2S`，供应商上传为 `S2C`。
- 留言“已读”表示留言回执；协作通知“已查看”表示通知状态；文件没有“已读”状态。
- 文件和留言删除属于公司内部管理动作。即使供应商角色被误授删除权限，服务端仍拒绝供应商删除。

## 并发和已读审计

- 项目数据写操作获取共享门控锁，再获取相关业务行锁；管理权限/账号/配置的事务获取排他门控锁。读取详情与摘要不获取排他项目行锁。详见[并发与错误响应契约](并发与错误响应契约-2026-09-23.md)。
- 同一标记已读请求按项目生成 `MESSAGE_READ` 汇总审计，`targetType=project`、`targetId=项目ID`，详情为 `{projectId,messageIds,count}`；重复已读不重复生成审计。该审计不再转换为项目动态，回执更新仍发送实时通知。
- 已删除留言的图片保留 30 天后由后台清理实体文件与图片记录；留言、回执、审计和项目动态不会因此删除。

## 状态与验收

- 每个子项目独立经历草稿、进行中、待公司验收、已完成和已终止流程。
- 只有供应商账号可以提交验收；提交后进入 `PENDING_CONFIRMATION`，供应商可在具备 `project:withdraw` 权限时撤回。
- 只有公司内部具备验收权限且可见该项目的账号可以确认或驳回。
- 全部子项目均为草稿时，主项目为草稿；任一子项目开始后，主项目为进行中。
- 全部子项目验收完成时，主项目在最后一次确认的同一数据库事务内自动变为已完成并记录完成时间。
- 全部子项目均已结束且至少一个已终止时，主项目为已终止；重新开始可恢复的子项目会重新计算主项目状态。
- 存在待验收子项目时，禁止修改主项目公共资料，避免验收期间资料变化。

## 主要接口

- `GET/POST /api/v1/project-groups`：查询或创建主项目。创建时必须同时提供至少一个子项目名称。
- `GET/PUT/DELETE /api/v1/project-groups/{id}`：查看、更新或删除符合条件的主项目。
- `POST /api/v1/project-groups/{id}/projects`：在主项目下新增子项目并继承公共资料。
- `GET/PUT/DELETE /api/v1/projects/{id}`：查看、修改名称与说明或删除子项目。
- `/api/v1/projects/{id}/files`、`/messages`、`/activities`：只处理指定子项目的协作内容。
- `POST /api/v1/projects/{id}/submit|withdraw|confirm|reject`：执行供应商提交/撤回或公司确认/驳回。

## 迁移与完整性

- schema v9 建立主项目与子项目关系并把 `project_group_id` 收紧为非空。
- schema v10 删除旧 `project_members` 表和 `project:member` 权限，补充供应商撤回权限，并为主项目、子项目负责人及公共元数据增加外键和一致性检查。
- v10 升级前会检查创建人、负责人、课别、字典引用和主子项目一致性；数据异常时中止升级，不自动猜测或篡改业务数据。
- 升级必须显式执行 `--migrate-database`；正常启动只验证当前 schema，不自动迁移。
