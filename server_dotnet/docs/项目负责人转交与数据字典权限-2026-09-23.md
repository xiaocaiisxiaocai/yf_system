# 项目负责人转交与数据字典权限

本契约补充并部分取代 [主项目与子项目协作契约](主项目与子项目协作契约-2026-09-16.md) 和 [Robot 料号与创建人负责制](Robot料号与创建人负责制-2026-09-23.md) 中"负责人不可更换""旧项目不因创建历史授予访问权"以及"目录管理使用 `config:manage`"的约定。

## 新增权限点

| ID | 编码 | 名称 | 类型 | 上级 |
|---:|---|---|---|---|
| 48 | `system:dict` | 数据字典 | MENU | — |
| 49 | `dict:manage` | 数据字典管理 | ACTION | 48 |
| 50 | `project:transfer` | 变更项目负责人 | ACTION | 2（项目列表） |

迁移 `20260924025646_AddDictionaryAndOwnerTransferPermissions`：

- 仅在已有权限目录的数据库中插入以上三项；空库由 `BootstrapSeedCatalog` 在初始化时写入完整目录。
- 原来拥有 `config:manage` 的角色同时获得 `system:dict` 与 `dict:manage`，升级后原有的字典维护能力不变。
- 内置"系统管理员"获得全部三项。
- 升级必须显式执行 `--migrate-database`。

## 公司内部的项目访问范围

内部账号在拥有 `project:list` 的前提下，满足以下任一条件即可查看主项目及其全部子项目：

1. 当前负责人；
2. **主项目创建人**（`project_groups.created_by`）；
3. 拥有 `project:view_all`。

- 创建人访问权不随负责人转交而丢失。子项目的创建人如果不是主项目创建人，不因此获得额外访问权。
- 项目列表、详情、文件、留言、动态、协作通知、实时推送、复制履历和工作台统一使用上述范围。
- 验收人 = 启用的内部账号，拥有 `project:list` 与 `project:confirm`，并满足上面三个条件之一。
- 留言、文件邮件提醒的内部收件人仍只有当前负责人；创建人和全局查看人不因可见而收到这两类邮件。

## 变更项目负责人

`PUT /api/v1/project-groups/{id}/responsible`，请求 `{ "responsibleUserId": 123 }`，返回 `ProjectGroupResponse`。

- 仅内部账号；需要 `project:list`、`project:transfer`，并且当前能访问该主项目。
- 新负责人必须是启用的内部账号，并通过启用角色拥有 `project:list`；不能与当前负责人相同。
- 存在待验收（`PENDING_CONFIRMATION`）子项目时返回 409：验收人和待验收提醒都依赖负责人，验收期间保持稳定。主项目处于草稿、进行中、已完成或已终止时都允许转交。
- 课别改为新负责人的有效直属课别；没有有效课别时为空。
- 负责人和课别同步到**全部**子项目，包括已完成的子项目，因为访问权跟随负责人。已完成子项目的其余验收快照（工令号、型号等）不变。
- 审计：主项目写 `PROJECT_GROUP_TRANSFER`（`project_group`，含负责人和课别的 changes）；每个子项目写 `PROJECT_UPDATE`，从而产生"编辑项目"动态并触发实时刷新。
- 原负责人既不是创建人、也没有 `project:view_all` 时，转交后失去访问权。

`GET /api/v1/project-owner-options` 返回可选的新负责人 `{id, employeeNo, realName, sectionId?, sectionName?}[]`，要求内部账号并拥有 `project:list` 与 `project:transfer`。可选范围与上面的新负责人条件一致，课别可以为空。

## 数据字典权限

- 优先级字典和 Robot 料号目录的维护（新增、编辑、停用、删除），以及 `GET /api/v1/robot-part-supplier-options`，改为要求 `dict:manage`，不再接受 `config:manage`。
- 项目表单读取优先级和料号选项仍按 `project:create` 或 `project:update` 判断，不受影响。
- 前端"数据字典"菜单使用 `system:dict`，页面要求 `dict:manage`；"系统参数"菜单仍使用 `system:config` / `config:manage`。

## 供应商账号角色的授权上限

非系统管理员给供应商账号分配角色（新建账号、重新启用账号、供应商角色下拉）时，角色权限必须不超过操作人自己的权限。`project:submit` 和 `project:withdraw` 只对供应商账号生效，内部账号无法实际使用，因此**不计入这一比较**；其余权限仍必须由操作人拥有。供应商角色本身仍只能包含固定的 8 项供应商权限。
