# OEM 绘图平台 - 数据库设计与接口规划

**版本**：V0.8（已实现；扫描引擎待定）
**更新日期**：2026-09-18
**前置文档**：[OEM绘图平台-需求文档-2026-09-18.md](./OEM绘图平台-需求文档-2026-09-18.md)

本文档覆盖 OEM 平台新增的数据库对象、状态边界和接口。生产后端继续使用 ASP.NET Core 10、EF Core、Pomelo/MySqlConnector、camelCase JSON、Bearer + 刷新会话轮换和 EF Core 迁移；普通业务读写使用 EF Core，只有行锁、命名锁和其他已审查的原子边界使用参数化原生 SQL。

> V0.8 变更：后端（`Yf.Api/Modules/Oem`）、前端（`web/src/oem`）、部署与维护脚本已按本文实现；实现细节与本文的差异和补充见文末“实现说明”。
>
> V0.7 变更：扫描引擎改为待定；§3.4 保留与引擎无关的扫描要求，ClamAV 和 Windows Defender 列为候选方案。
>
> V0.6 变更：扫描引擎选定开源 ClamAV，新增 §3.4 部署、调用、配置、结果映射与限制。
>
> V0.5 变更：
> - 审批流增强：模板可按事业部/部门/课别绑定；审批人来源增加事业部主管和指定人员，指定人员支持或签/会签；每个节点可配置“发起人就是本节点审批人”时改由备用审批人审批、本节点免审或禁止发送；全部节点免审时扫描通过后直接发布；
> - 取消 V0.4 的“同一审批人合并”规则：组织上不存在兼任，同一人出现在多个节点视为模板配置错误，发送失败；
> - 不在任何课别下的内部员工不能创建和发送公司出站传递单；
> - 邮件通知审批人和接收人：待审批邮件发给当前审批人；发布邮件发给全部接收人（公司出站为目标厂商全部启用账号，OEM 入站为全部具备查看+下载权限的内部员工），逐人单独发送。
>
> V0.4 变更：
> - 确认单服务器、单端口、单进程部署，删除多机相关表述；租约保留，用于 IIS 回收重叠和进程重启恢复；
> - 新增 §0.1 业务线双向隔离的实现要求及对应权限点、接口和回归项；
> - 取消 V0.3 的独立操作凭证目录 `OemOperationJournalRoot`；数据库恢复改为“维护脚本写恢复标记 → 启动核对 → 缺失统一 `MISSING_UNVERIFIED`、孤儿文件删除”；
> - `oem_file_operations` 收窄为只负责隔离区→正式区移动的 `oem_file_promotions`；删除沿用文件行上的清理租约；
> - V0.3 中以段落描述的表全部改为带类型的表格；`approval_status` 明确为接口派生字段，不是数据库列；去掉与清理租约重复的 `purge_claimed_at`；`stored_name` 兼作 V0.3 的 `file_uuid`；
> - 传递单增加 `ABANDONED` 状态及关闭原因字段。

## 0. 与现有系统的关系

| 现有对象 | 处理方式 |
|---|---|
| `departments` | 复用，增加当前主管字段 |
| `users` | 只复用内部账号；OEM 外部账号进入独立表 |
| `refresh_tokens` | 不复用；OEM 使用独立 `oem_refresh_tokens` |
| `files` / `upload_sessions` | 不复用业务表；复用分片、合并、哈希、路径和崩溃恢复代码 |
| `system_configs` | 复用表结构，但使用 `oem.*` 独立配置键 |
| `audit_logs` | 复用，增加 actor realm/account 快照字段以区分内部与 OEM 账号 |
| `email_outbox` | 复用发送队列，增加 recipient realm/account 快照字段；OEM 邮件不关联 `project_id` |
| `permissions` / `roles` / `role_permissions` | 复用结构，增加 OEM 内部权限点 |
| 现有 `App.StorageRoot` | 继续存放供应商协作文件并进入备份；OEM 文件使用独立且不备份的 `OemStorageRoot` |

现有 `files.project_id`、`files.uploader_id`、`upload_sessions.project_id` 和 `upload_sessions.uploader_id` 都绑定现有项目及用户表；OEM 账号又必须独立建表，因此不能只给现有表增加一个 `oem_transfer_id`。代码复用和表复用必须分开。

### 0.1 业务线双向隔离

供应商协作平台与 OEM 平台共享进程和数据库，但对使用者双向不可见。实现要求：

| 层面 | 要求 |
|---|---|
| 令牌 | OEM 令牌带 `realm=oem`；鉴权中间件对除 `/api/v1/oem/*` 外的全部路由拒绝 `realm=oem`，对 `/api/v1/oem/*`（`/oem/auth/*` 除外）只接受 `realm=oem` 或具备对应 `oem:*` 权限的内部账号令牌 |
| 供应商账号 | 访问任何 `/api/v1/oem/*` 一律 403，与其角色无关；角色分配时拒绝把含 `oem:*` 权限的角色授予供应商账号，权限计算时也对供应商账号忽略 `oem:*` |
| 协作平台接口 | 项目、工作台、消息、文件、统计、搜索、通知接口的查询只针对协作平台表，不联查任何 `oem_*` 表，不返回 OEM 数据 |
| OEM 接口 | 只查询 `oem_*` 表及审批所需的最小内部账号信息（姓名、工号），不返回供应商、项目或协作文件数据 |
| 实时推送 | OEM 账号不能连接现有项目 SignalR Hub；OEM 事件不推送到现有 Hub。OEM 页面采用轮询；如需实时推送，使用独立 Hub 路径 |
| 系统管理页面 | 现有审计日志、邮件队列查询默认排除 `actor_realm=oem`、`OEM_*` action 和 `oem_transfer_id` 非空的记录；OEM 审计通过 `/oem/audit-logs` 按 `oem:audit_view` 查看 |
| 邮件提醒规则 | 现有 `notify.*` 规则只作用于协作平台；OEM 使用独立 `oem.notify.*` 键，两边开关互不影响 |
| 前端 | OEM 使用独立子路径（如 `/oem/`）、独立登录页和独立令牌存储键；内部员工在 OEM 入口使用同一内部登录状态，但 OEM 菜单仅在具备任一 `oem:*` 权限时显示；OEM 账号前端不加载协作平台路由和菜单 |
| Cookie | OEM 刷新 Cookie 使用独立名称，Path 限定为 `/api/v1/oem/auth`；OEM 下载凭证 Cookie 使用独立名称，Path 限定为 `/api/v1/oem/files` |

### 0.2 单节点部署

- 一台服务器、一个 IIS 站点、一个对外端口；不支持多机横向扩展；
- `OemStorageRoot` 为本机本地绝对路径；
- 后台任务运行在应用进程内。IIS 应用池回收时新旧工作进程可能短暂重叠，进程也可能在任务中途被终止，因此扫描、移动、清理和下载仍使用数据库租约和版本号（fencing），保证同一时刻只有一个执行者、重启后可恢复；这不是为多机部署设计的。

索引：`(oem_company_id, lifecycle_status)`、`(internal_sender_user_id)`、`(oem_sender_account_id)`、`(lifecycle_status, released_at)`。

发送人约束：

- `INTERNAL_TO_OEM`：`internal_sender_user_id` 必填，`oem_sender_account_id` 为空；
- `OEM_TO_INTERNAL`：`oem_sender_account_id` 必填，`internal_sender_user_id` 为空；
- MySQL 5.7 不依赖 CHECK 约束保证该规则，服务层和迁移回归都必须校验。

`lifecycle_status`（只表示业务流程结果）：

- `DRAFT`：允许上传、移除附件和编辑标题说明；
- `SEALED`：已发送并冻结附件，等待扫描、审批或自动发布；
- `RELEASED`：已发布；各文件能否下载由文件自身状态决定；
- `REJECTED`：公司出站审批被驳回；
- `BLOCKED`：病毒、不可扫描或耗尽重试后的最终安全失败；
- `CANCELLED`：管理员带原因终止尚未发布的传递；
- `ABANDONED`：草稿被发送人删除或超过草稿期限被系统清理，附件实体已进入清理，记录保留供审计。

扫描汇总、审批进度、部分/全部删除及缺失数量按 §2.5 派生，不写入传递单，也不用文件状态覆盖业务结果。

接口返回的 `approvalStatus` 是派生字段，不是数据库列：出站方向由 `oem_flow_instances.status` 映射为 `WAITING_SCAN / PENDING / APPROVAL_BLOCKED / APPROVED / SKIPPED / REJECTED / CANCELLED`（`SKIPPED` 表示全部节点按策略免审），草稿阶段为空；入站方向固定为 `NOT_REQUIRED`。

接收范围不另建成员表：公司出站按 `oem_company_id` 匹配该厂商全部启用账号；OEM 入站按内部账号是否同时具备 `oem:transfer_view` 和 `oem:file_download` 动态判断。

不增加 parent/revision/version 等关联字段；修正文件创建新的独立传递单。

索引：`(transfer_id)`、`(payload_status, purge_due_at)`、`(payload_status, purge_next_attempt_at)`。

`payload_status`（存储事实）：

| 值 | 含义 | 可访问 |
|---|---|---|
| `QUARANTINED` | 位于隔离区，等待或正在扫描 | 否 |
| `PROMOTING` | 扫描通过，正在移入正式区 | 否 |
| `AVAILABLE` | 位于正式区 | 按 §2.3 判断 |
| `PURGE_PENDING` | 已到期或需安全清理，等待/正在删除实体 | 否 |
| `PURGED` | 实体已删除 | 否 |
| `STORAGE_LOST` | 日常运行中发现实体非预期缺失 | 否 |
| `MISSING_UNVERIFIED` | 数据库恢复后实体缺失，无法区分正常删除还是异常丢失 | 否 |

删除按文件独立触发。未下载文件仍按发布期限或自身首次接收时间处理；页面汇总文件状态，不改变传递单业务结果。

#### 1.9.3 发送时解析

发送事务内按模板解析全部启用节点，结果写入快照并创建实例、节点和任务：

1. 发起人必须归属一个启用的**课别**。直属部门或事业部、不在任何课别下的内部员工不能创建和发送公司出站传递单，创建草稿和发送时都校验；
2. 主管类节点取发起人组织路径上对应层级的 `leader_account_id`：
   - 未配置主管，或主管已禁用/无 `oem:flow_approve`：发送失败，提示管理员维护主管；
   - 主管就是发起人本人：按 `self_policy` 处理：`DESIGNATED` 改用本节点 `FALLBACK` 人员（按 `ANY` 处理，发起人本人从名单中剔除）；`SKIP` 本节点记为免审；`BLOCK` 发送失败；
3. `SPECIFIED_USERS` 节点：先从名单中剔除发起人本人和不合格人员；剔除发起人后名单为空时按 `self_policy` 处理；因人员失效导致名单为空、或 `ALL` 模式下有人失效时，发送失败；
4. 同一审批人出现在同一实例的多个节点中属于模板配置错误，发送失败并提示调整模板（组织上不存在兼任，出现即视为配置问题）；
5. 全部启用节点都被免审时，实例状态直接为 `SKIPPED`：传递单扫描通过后按无需审批直接发布，快照和审计记录每个节点的免审原因；
6. 任一步失败时整个发送事务回滚，传递单保持草稿。

#### 1.9.5 推进规则

- 发送成功后实例为 `WAITING_SCAN`（全部免审时为 `SKIPPED`），任务为 `WAITING`；
- 全部文件 `CLEAN` 且移动完成后，实例激活为 `IN_PROGRESS`，第一个未免审节点置 `PENDING`，其全部任务置 `PENDING` 并给这些审批人发邮件；
- `SINGLE`/`ANY`：任一任务通过即节点通过，其余任务置 `NOT_NEEDED`；`ALL`：全部任务通过节点才通过；
- 任一任务驳回：节点、实例置 `REJECTED`，其余未完成任务置 `CANCELLED`，传递单置 `REJECTED`；
- 节点通过后推进到下一个未免审节点；全部完成后实例 `COMPLETED`，在同一事务中发布传递单、初始化删除期限、为接收方入队通知；
- 激活和每次决定时重新校验当前节点审批人的启用状态和 `oem:flow_approve` 权限：`ANY` 节点还有至少一名有效审批人时继续，否则置 `APPROVAL_BLOCKED`；`SINGLE`/`ALL` 节点有人失效即 `APPROVAL_BLOCKED`；阻断时通知发送人和 `oem:approval_recover` 管理员。账号禁用/撤权时主动检查相关实例，巡检兜底；
- 模板、适用范围、组织主管之后的变化不改写已创建的实例；
- 只有 `PENDING` 任务的指派人能审批，重复或过期操作返回冲突；
- 重复 send 依靠版本和唯一 `transfer_id` 返回已有结果，不重复建实例。

`oem:approval_recover` 可对异常未完成任务改派，或终止未发布的传递单，必须填写原因：

- 改派：新审批人必须合格、非发送人且不在本实例其他节点中；旧任务置 `SUPERSEDED`，新建任务并以 `replaces_task_id` 关联；改派与迟到审批用行锁和版本号互斥，只允许一次有效决议；已完成节点不变；
- 改派后重新校验：扫描未完成继续 `WAITING_SCAN`，扫描完成且当前节点有效才恢复 `IN_PROGRESS`，否则保持 `APPROVAL_BLOCKED`；
- 终止：实例、节点和未完成任务置 `CANCELLED`，传递单置 `CANCELLED`，附件按安全清理期限处理；
- 管理员不能代替审批人审批通过，也不能把节点改为免审。

扫描最终失败时，等待中的实例、节点和任务置 `CANCELLED`。

- 每次只接受单段合法 Range；完成响应后在事务中锁定会话，把重叠/相邻区间取并集，不累加重复字节；
- 只有合并后覆盖完整的 `0..expected_size-1` 才把会话标为 `COMPLETED`；
- HEAD、304、416、部分发送失败、断开连接和生成 URL 都不算完成；完整 GET 也必须完成响应才记全区间；
- 限制合并后区间数、请求频率和并行数；超过限制拒绝新请求，不丢弃已有区间，也不误报完成；
- 不能跨账号或跨会话汇总字节。

首个 `recipient_side=1` 的完成会话使用条件更新（`first_recipient_download_at IS NULL`）写入文件：

```
first_recipient_download_at = completed_at
purge_due_at =
  KEEP                        -> null（只记录首次接收，不自动删除）
  AFTER_RELEASE               -> 保持发布时的 expires_at
  AFTER_FIRST_RECEIPT         -> completed_at + receipt_grace
  FIRST_RECEIPT_OR_DEADLINE   -> min(completed_at + receipt_grace, expires_at)
```

发布事务内为全部文件初始化 `purge_due_at`：`KEEP`、`AFTER_FIRST_RECEIPT` 为空；`AFTER_RELEASE`、`FIRST_RECEIPT_OR_DEADLINE` 设为 `expires_at`。重复回执不能延长期限。时间一律使用数据库 UTC。纯首次接收模式无人下载时不自动到期，界面要明示；绝对期限可以截短宽限期。

发送方、审批人和预览会话可写下载审计，但 `recipient_side=0`，不能触发首次接收。

活动租约：请求准入与清理认领锁定同一文件行，避免“检查通过后、打开文件前”被清理穿透；租约带 fencing，失去租约立即停止读取。请求截止时间取会话硬截止、单请求最长时长、到期后排空期限三者最早值。删除遇到仍被占用的文件应重试，不能谎报 `PURGED`。

下载凭证可参考现有 `MediaGrantService` 的签名和 HttpOnly Cookie 机制，但使用独立用途类型和 Cookie 名称，额外绑定 realm、账号、登录会话、文件 UUID、下载会话 ID、purpose 和有效期。短期凭证可续签，但受会话硬截止限制，不能把媒体的五分钟有效期当成数 GB 下载的完整生命周期。

### 1.11 审计与邮件队列兼容

`audit_logs` 增加 `actor_realm VARCHAR(16) NULL`、`actor_account_id BIGINT UNSIGNED NULL`，保留现有 `user_id`/`employee_no` 供协作平台使用；OEM 账号操作只写 `actor_realm=oem` 和 `actor_account_id`，不写入 `user_id`，避免内部 user id 与 OEM account id 混淆。OEM 事件使用 `OEM_TRANSFER_*`、`OEM_SCAN_*`、`OEM_APPROVAL_*`、`OEM_DOWNLOAD_*`、`OEM_PURGE_*`、`OEM_RECONCILE_*` 等 action。

邮件规则：

| 事件 | 收件人 | 默认 |
|---|---|---|
| 待审批（节点激活、改派产生新任务） | 当前节点每位 `PENDING` 任务的审批人 | 开启 |
| 公司出站发布 | 目标厂商全部启用 OEM 账号 | 开启 |
| OEM 入站发布 | 全部同时具备 `oem:transfer_view` 和 `oem:file_download` 的启用内部员工 | 开启 |
| 审批通过/驳回、审批阻断、扫描最终失败、存储丢失/原因待核实 | 发送人（OEM 方向为发送账号本人）；审批阻断另发 `oem:approval_recover` 管理员 | 开启 |

- 安全告警不向未获得文件访问权的接收方暴露任何内容。

## 2. 状态与事务边界

### 2.1 公司 → OEM

```
DRAFT
  → 发送并冻结清单（同一事务创建 WAITING_SCAN 审批实例）
SEALED + 扫描中
  → 全部 CLEAN 且移动完成
激活审批实例（失效则 APPROVAL_BLOCKED）
  → 全部未免审节点通过（全部免审时跳过此步）
RELEASED（OEM 厂商全部启用账号可下载）
  → 文件逐个首次接收或到期
文件 PURGE_PENDING → PURGED；传递单保留 RELEASED
```

扫描暂时故障保持 `SEALED`、有限重试；最终失败才 `BLOCKED`。审批驳回为 `REJECTED`，终止为 `CANCELLED`。终态单据的文件修正须新建传递单。

### 2.2 OEM → 公司

```
DRAFT
  → 发送并冻结清单
SEALED + 扫描中（approvalStatus=NOT_REQUIRED）
  → 全部 CLEAN 且移动完成
RELEASED（具备 view + download 权限的内部账号可下载）
  → 文件逐个首次接收或到期
文件 PURGE_PENDING → PURGED；传递单保留 RELEASED
```

### 2.3 文件访问条件

接收方预览、下载和每个 Range 请求都重新判断：

```
transfer.lifecycle_status == RELEASED
&& file.payload_status == AVAILABLE
&& file.scan_status == CLEAN
&& (file.purge_due_at IS NULL || 当前时间 < file.purge_due_at)
&& 当前账号仍启用（OEM 账号还要求所属厂商启用）
&& 当前账号仍属于接收范围
&& 系统未处于恢复核对模式（§3.3）
```

发送侧及审批审阅同样要求 `CLEAN`、`AVAILABLE`、未到 `purge_due_at`、账号/厂商启用且具备对应权限。`DRAFT/SEALED` 内容只供实际发送人及已激活任务的审批人访问；`RELEASED` 后 OEM 同厂商员工共享发送侧查看，内部发送人仍需 view + download。`BLOCKED/REJECTED/CANCELLED/ABANDONED` 禁止访问内容。发送侧和审批审阅的 `recipient_side=0`，只有实际草稿发送人可修改附件。

任何前端隐藏、旧 token、已生成下载会话或历史通知都不能绕过实时判断。扫描完成前，发送方和审批人同样不能预览或下载。

### 2.4 物理删除

数据库事务不能与文件系统删除组成同一原子事务，因此采用可重试状态机：

1. 以条件更新认领到期文件，写 `PURGE_PENDING`、清理租约和审计；
2. 立即拒绝新下载；已开始的下载限时排空，到达空闲/绝对/排空截止时间即取消请求、释放句柄；
3. 在 `OemStorageRoot` 边界内解析并删除实体文件；
4. 删除成功，或实体已不存在（该文件已处于 `PURGE_PENDING`，删除已是既定结果），均更新为 `PURGED`、写 `purged_at` 并审计；
5. 删除失败保留 `PURGE_PENDING`，按退避重试并告警。

### 2.5 汇总规则与发布互斥

扫描任务使用 `PENDING/RUNNING/CLEAN/INFECTED/ERROR/UNSCANNABLE`；文件对外状态把 `RUNNING` 映射为 `SCANNING`，重试中的 `ERROR` 不代表终态失败。单据扫描汇总只读派生：存在 `INFECTED` 优先，其次 `UNSCANNABLE`，再次耗尽重试的 `ERROR`；否则存在运行任务为 `SCANNING`、存在待执行/重试任务为 `PENDING`，非空附件全部 `CLEAN` 才为 `CLEAN`。列表返回各状态数量和失败原因，不用一个总状态掩盖其他问题。

发布必须在文件集已冻结、无活跃上传、所有文件 `CLEAN` 且 `AVAILABLE`、发送账号/厂商有效，以及公司出站审批完成时，通过一次条件更新执行。草稿扫描完成不会自动发送；`SEALED` 时若全部扫描早已完成，send 后可立即推进。扫描完成与 send 的竞争由 transfer 行锁和版本检查串行化，不能漏推进或重复发布。

`payload_status` 是存储事实，`lifecycle_status` 是流程事实。文件进入 `PURGE_PENDING/PURGED` 不改变 `RELEASED`；其他未到期的 `AVAILABLE` 文件继续可下载。详情返回 `availableCount`、`purgePendingCount`、`purgedCount`、`missingCount`（含 `STORAGE_LOST` 和 `MISSING_UNVERIFIED`）；全部文件删除后仍保留 `RELEASED` 和历史审批结果，页面显示“全部文件已清理”。接口按文件 `purge_due_at` 实时拒绝到期访问，不等清理任务执行。

## 3. 配置与独立存储

### 3.1 应用私有配置

外部 JSON 配置新增：

- `App:OemStorageRoot`：OEM 文件专用根目录；
- `App:OemScanner`：扫描引擎类型、本机连接参数、基础超时和每 GB 附加超时（具体字段随引擎选定）；不得进入网页 `system_configs` 或日志。

启动时验证 `OemStorageRoot`：必须是本机本地绝对路径，不得与网站、程序、配置、现有 `StorageRoot`、备份目录互相包含，不允许重解析点；目录只授予应用池和受控扫描身份所需权限，禁止执行。目录下固定划分 `uploads/`（分片）、`quarantine/`（隔离区）、`available/`（正式区）三个子目录，保证同卷重命名。

### 3.3 不备份与数据库恢复

现有维护脚本继续只复制 `App.StorageRoot`，不得把 `OemStorageRoot` 加入备份清单。配置文件会备份路径字符串，但不复制该路径中的文件。

部署和运维检查还必须证明操作系统备份、VSS、虚拟机/云盘快照、NAS 同步和第三方备份策略排除了 `OemStorageRoot`。应用代码只能保证自身备份脚本不复制，不能替代基础设施核对。

不保存独立于数据库的删除凭证，恢复规则如下：

1. `maintain-iis.ps1 -Restore` 在导入数据库后写入 `oem.storage.reconcile_required=RESTORED`；不经维护脚本手工恢复数据库时，运维人员必须执行 `dotnet Yf.Api.dll --oem-mark-restored` 写入同一标记；
2. 应用启动发现该标记后进入恢复核对模式：OEM 文件预览、下载、上传初始化和发送接口返回 503，其余 OEM 元数据接口可读；
3. 先按 §1.8 恢复未完成的移动；
4. 对数据库中 `QUARANTINED / PROMOTING / AVAILABLE` 的文件核对实体路径、大小：
   - 实体存在且一致：保持原状态；
   - 实体缺失：置 `MISSING_UNVERIFIED`；
   - 大小不一致：置 `MISSING_UNVERIFIED` 并告警，不得提供下载；
5. 数据库中 `PURGE_PENDING` 且实体缺失的文件置 `PURGED`（删除在备份时已是既定结果）；
6. `OemStorageRoot` 中没有数据库记录的实体文件和分片目录（备份之后上传的内容）视为孤儿，物理删除并审计 `OEM_RECONCILE_ORPHAN_PURGED`（只记录 UUID 和大小）；
7. 已过 `purge_due_at` 的文件照常进入清理；
8. 全部完成后清除标记，写审计 `OEM_RECONCILE_COMPLETED`，通知受 `MISSING_UNVERIFIED` 影响的发送人。

日常运行（无恢复标记）时，一致性检查发现 `AVAILABLE` 等状态的文件实体缺失，置 `STORAGE_LOST` 并通知发送人。孤儿文件只清理创建时间超过上传会话最长有效期、且不被任何活动上传会话或移动记录引用的文件，避免误删正在合并的内容。

这一方案的已知局限：数据库恢复后，“备份之后按策略正常删除”和“异常丢失”都显示为“原因待核实”，不再细分。两者都不可下载，影响只在于显示原因。

### 3.4 扫描引擎（待定）

具体扫描引擎暂未选定，后续再定。无论选哪种，都必须满足：

- 扫描引擎安装在同一台服务器上，只在本机调用，不把文件上传到任何在线扫描服务；
- 应用内通过扫描器接口调用，业务流程、表结构和 `oem.scan.*` 参数与具体引擎无关；更换引擎或增加第二引擎时只替换接口实现；
- 扫描结果统一映射为 `CLEAN / INFECTED / UNSCANNABLE / ERROR`：查出威胁为 `INFECTED`；加密压缩包、超出引擎扫描限制为 `UNSCANNABLE`；出错、超时、引擎不可用为 `ERROR`，按退避重试，耗尽后整单 `BLOCKED`；
- 引擎不能明确报告加密压缩包时，由应用在扫描前自行识别加密的 ZIP、RAR、7z 并判为 `UNSCANNABLE`；
- `oem.upload.max_file_size` 不得超过所选引擎实测的可扫描上限，上传初始化时就拒绝超限文件；
- 扫描超时按文件大小计算（基础时长 + 每 GB 附加时长）；
- 记录引擎名称、引擎版本和病毒库版本；病毒库超过 `oem.scan.max_signature_age_hours` 未更新时告警，是否暂停放行由 `oem.scan.block_on_stale_signatures` 决定，默认只告警。

引擎选定前开发可先实现扫描器接口和一个仅用于开发和测试环境的模拟实现；生产环境未配置真实扫描引擎时，扫描任务一律返回 `ERROR`，文件保持不可用，不得放行。

#### 候选方案一：ClamAV（开源）

开源的 **ClamAV**（GPL-2.0，有官方 Windows 版本）。ClamAV 作为独立程序安装，本系统只通过本机网络接口调用，不链接其代码，许可证不影响本系统代码；它不打包进发布 zip，由部署文档说明安装步骤。

**部署**

- `clamd`（扫描服务）和 `freshclam`（病毒库更新）以 Windows 服务运行在同一台服务器上，`clamd` 只监听 `127.0.0.1`；
- `clamd` 的服务账号只对 `OemStorageRoot\quarantine\` 有只读权限，对其他目录无权限；
- 常驻内存约 1 GB 以上（病毒库加载），服务器内存需要预留；
- 病毒库需要从 ClamAV 官方镜像更新：服务器需能经代理访问外网，或由公司内部镜像同步。

**调用方式**

- 扫描任务把隔离区文件的绝对路径交给 `clamd` 做路径扫描，文件内容不经过应用进程转发，适合数 GB 文件；
- 扫描前后通过 `clamd` 的版本命令读取引擎版本和病毒库版本，写入 `engine_version`、`signature_version`；
- 应用内以扫描器接口封装，以后替换或增加第二引擎时不改表结构。

**clamd 关键配置**（与 `oem.scan.*` 参数保持一致，部署检查核对）

| 配置 | 要求 |
|---|---|
| `MaxFileSize` / `MaxScanSize` | 不小于 `oem.upload.max_file_size` / 压缩包解压上限 |
| `MaxRecursion` / `MaxFiles` | 等于 `oem.scan.archive_max_depth` / `oem.scan.archive_max_entries` |
| `AlertExceedsMax` | `yes`：超出限制的文件报告为命中，而不是静默放过 |
| `AlertEncrypted` | `yes`：加密压缩包、加密文档报告为命中 |
| `ScanArchive` / `ScanPDF` / `ScanOLE2` | `yes` |

**结果映射**

| clamd 返回 | 扫描结果 |
|---|---|
| `OK` | `CLEAN` |
| `FOUND`，且检测名为 `Heuristics.Encrypted.*` 或 `Heuristics.Limits.Exceeded.*` | `UNSCANNABLE`（整单 `BLOCKED`） |
| 其他 `FOUND` | `INFECTED`（整单 `BLOCKED`） |
| `ERROR`、超时、连接失败 | `ERROR`，按退避重试，耗尽后整单 `BLOCKED` |

**限制与注意**

- ClamAV 对单个文件的可扫描大小有硬上限（与版本有关，需在部署版本上实测）。`oem.upload.max_file_size` 不得超过实测可扫描的上限，上传初始化时就拒绝超限文件，避免上传几 GB 后才因无法扫描而阻断；
- 扫描超时按文件大小计算（基础时长 + 每 GB 附加时长），不用固定值；
- 病毒库超过 `oem.scan.max_signature_age_hours` 未更新时，就绪检查告警并通知运维；是否因此暂停放行由 `oem.scan.block_on_stale_signatures` 决定，默认只告警；
- ClamAV 对新型 Windows 恶意程序的检出率低于商业产品，它提供的是基础防护；安全要求提高时可在扫描器接口后增加第二引擎，两个引擎都通过才算 `CLEAN`；
- 默认不开启“含宏 Office 文档一律拦截”（`AlertOLE2Macros`），因为这会拦下大量正常的带宏表格；是否开启由业务决定。
- 需要单独安装：可写入 `deploy/install-iis.ps1` 由安装脚本自动安装、配置并检查服务状态；服务器不能上外网时，安装包和病毒库需手工拷入或搭建内网镜像。

#### 候选方案二：Windows Defender（系统自带）

- Windows Server 自带，无需安装，病毒库随 Windows 更新，检出率通常高于 ClamAV；
- 不是开源软件；
- 不会明确报告加密压缩包，需由应用自行识别；
- 服务器装有其他杀毒软件时 Defender 会进入被动模式，不能用于扫描。

## 6. 后台任务

应用进程内运行以下任务，均使用数据库租约，保证 IIS 回收重叠期间不重复执行，进程重启后可恢复：

1. **扫描任务**：认领隔离文件，通过扫描器接口调用本机扫描引擎（§3.4），记录结果，推动移动、审批激活或发布；
2. **移动任务**：执行和恢复隔离区→正式区的移动（§1.8）；
3. **清理任务**：认领到期文件、废弃草稿、过期上传会话和安全隔离文件，等待活动下载排空后物理删除，失败重试；
4. **一致性任务/启动检查**：恢复模式按 §3.3 核对；日常模式定期发现实体缺失（`STORAGE_LOST`）和孤儿文件。

任务异常时，新待扫描文件保持不可用，到期文件由请求时的期限检查拦截；已发布且仍有效的文件不因清理任务停止而全部失效。内部运维就绪检查暴露扫描积压、扫描器不可用、恢复核对未完成和清理失败，公共健康响应不泄漏文件名、路径或病毒内容。

## 7. 必要回归与验收

实现时至少覆盖：

- **业务线隔离**：供应商账号访问任何 `/oem/*` 均被拒绝；OEM 令牌访问任何非 `/oem/*` 接口均被拒绝；协作平台项目、工作台、消息、通知、审计、邮件队列接口的响应中不含 OEM 数据；OEM 接口响应中不含供应商、项目和协作文件数据；含 `oem:*` 的角色不能授予供应商账号；OEM 账号无法连接项目 SignalR Hub；
- 两个 realm 不能跨业务线、跨 OEM 厂商或伪造方向；跨 realm 同名账号不共享限流桶和失败计数；
- 公司出站在扫描和审批完成前 OEM 不可见、不可下载；
- OEM 入站无需人工审批，但扫描未通过时内部不可预览或下载；
- 上传人自审、缺少课别及任一启用节点解析失败时发送回滚；模板/组织变更不改变发送快照；
- 模板按课别→部门→事业部→默认的顺序选用；主管发起时 `DESIGNATED`/`SKIP`/`BLOCK` 分别生效；全部免审时扫描通过后直接发布且审计记录免审原因；或签任一人通过即推进、会签需全部通过、任一人驳回即终止；同一人出现在多个节点时发送失败；
- 不在任何课别下的内部员工创建或发送出站传递单被拒绝；
- 待审批邮件只发给当前节点审批人；发布邮件发给全部接收人、逐人单发、不暴露其他收件人地址；撤权或禁用的接收人不收邮件；
- 审批人禁用/撤权会阻断，可以改派或终止；改派与迟到审批竞争时只允许一次有效决议；
- 发送后附件不能增删替换，模板变化不影响历史实例；
- 加密 ZIP/RAR/7z、病毒命中、扫描超时和不可扫描均失败关闭；扫描暂时错误能重试，最终错误才阻断；
- 多 GB 文件使用分片和流式处理，不整文件进入应用内存；
- 任意一名合法接收方完整下载只触发一次首次接收；发送方、预览、部分 Range、超量/重叠 Range、不同账号的零散区间、HEAD 和断线都不触发；
- 多附件按文件独立记录首次接收和删除时间，部分删除不影响其他文件；组合策略无人下载也按期到期；
- 宽限期内可重试；`PURGE_PENDING` 后新下载被拒绝；慢客户端被绝对截止取消；物理删除失败可恢复重试；
- 病毒/不可扫描文件和长期未发送草稿按独立期限清理，不受发送方选择的保留模板控制；草稿清理后传递单为 `ABANDONED`；
- 并发配额预留不超售；公司出站文件计入目标厂商配额；
- 移动前/后及数据库提交前后崩溃都能幂等恢复；
- OEM 文件不进入现有离线备份，基础设施快照排除项已核对；
- 通过维护脚本恢复数据库后：核对完成前内容接口返回 503；实体缺失的文件为 `MISSING_UNVERIFIED`；`PURGE_PENDING` 且缺失的为 `PURGED`；备份后上传的孤儿文件被删除；日常运行中的缺失为 `STORAGE_LOST`；
- 文件实体删除后，审批、扫描、下载和删除审计仍可查询且不含秘密；
- 通知发送前撤权能够取消发送。
