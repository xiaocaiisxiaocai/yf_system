# 项目复制与引用履历契约

项目复制只对公司内部开放。调用者必须同时拥有 `project:list`、`project:create`，并且在负责人范围或 `project:view_all` 范围内可见源项目。新项目名必填、全局唯一，且不能与源项目同名。源项目的工令号、机型、Robot 厂商和型号、负责人、课别、优先级、预计完成日期必须完整且当前关联仍有效，否则返回 409，要求先补齐源项目。

`POST /api/v1/projects/{id}/copy` 请求为 `{ "name": "新项目名" }`。成功返回 `{ project, copy }`；`copy` 包含 `copyId`、`sourceProjectId`、`targetProjectId`、`fileCount`、`totalBytes`、`createdAt`。新项目固定为 `DRAFT`，保留源项目供应商、说明、全部必填元数据和工令号，创建人与复制文件上传人均为当前操作人。

复制所有 `AVAILABLE` 文件，每个目标文件使用独立的存储路径，保留方向、原始文件名、扩展名、大小、MIME 和 SHA-256。留言、留言图片、留言回执、通知读取记录、既有状态记录、邮件、上传会话和历史动态不复制；目标项目只产生本次 `COPY` 初始状态记录和复制动态。

复制不设置项目、用户、文件数量或总容量配额。执行前按源文件记录以 checked 算术汇总字节并检查存储卷剩余空间。每个文件以流式方式复制，同时核对实际字节数和 SHA-256。源文件缺失、路径异常、哈希缺失或不匹配时，整个复制失败并清理本次生成的物理文件。

为避免大文件复制长期占用数据库锁，处理分两阶段进行：第一段短事务锁定并读取源项目、工令、全部文件状态和活动上传快照；事务外完成文件复制；第二段短事务重新鉴权并锁定源项目和文件，精确核对 `updated_at`、元数据、工令、文件 ID/状态/路径/大小/SHA 以及活动上传。任何变化都返回 409，并清理候选文件。数据库提交异常后会用独立连接核对复制记录；确认未提交时清理，确认已提交时返回成功；无法判定时保留候选文件并返回可诊断错误，避免删除可能已被提交记录引用的文件。

schema v7 新增 `project_copies` 和 `file_copy_refs`。两表保存项目名、文件名和操作人姓名快照；项目及文件外键保证引用不悬空。任一项目存在复制来源或派生履历时，项目删除接口明确返回 409。文件采用软删除，映射仍可显示当时文件名及当前删除状态。

`GET /api/v1/projects/{id}/copy-history` 返回 `{ source, copies, hasRestrictedRelations }`。来源和派生项目仅在调用者当前可见时返回；不可见关系不披露项目 ID、名称或快照，只把 `hasRestrictedRelations` 置为 `true`。`GET /api/v1/project-copies/{copyId}/files?page&pageSize` 分页返回文件映射，默认每页 20、最大 100；调用者必须同时可见来源和目标项目，否则按不存在处理。项目文件列表仅返回 `isCopiedReference` 布尔值，不泄露来源文件 ID。

审计动作是 `PROJECT_COPY`，目标是新项目，详情保留来源/目标快照、文件数和总字节。来源与目标各生成一条不包含对方项目名的通用复制动态，防止负责人变更后通过历史摘要泄露已失去权限的项目名称。提交后向来源和目标项目的当前可见用户发布 `activity` 实时刷新事件。

升级必须显式执行 `--migrate-database`；正常启动只验证 schema v7，不自动变更数据库。DDL 可重入，迁移历史只有在两张表结构均校验通过后才写入版本 7。
