# 项目复制与复制履历契约

> 文件名沿用历史名称；产品界面和业务描述统一使用“复制件”和“复制履历”。

## 权限与目标范围

- 项目复制只对公司内部开放。调用者必须拥有 `project:list`、`project:create`，并在负责人或 `project:view_all` 范围内可见源子项目。
- `POST /api/v1/projects/{id}/copy` 请求为 `{ "name": "新子项目名", "idempotencyKey": "调用方生成的任务键" }`。名称必填、全局唯一，且不能与源项目同名；幂等键最长 64 个字符。
- 目标是源子项目所在主项目下的新子项目，不会创建新的主项目，也不能跨主项目复制。
- 主项目已完成或已终止时禁止复制。目标子项目固定为 `DRAFT`，继承主项目当前的供应商、公共元数据及工令号，说明和文件来自源子项目。
- 源项目必填资料缺失或关联已失效时返回 409，要求先修复源项目资料。

## 后台任务接口

- `POST /api/v1/projects/{id}/copy` 在任务持久化后返回 `202 Accepted`，`Location` 指向 `/api/v1/project-copy-jobs/{jobId}`；响应体就是扁平任务对象，不再同步返回 `{ project, copy }`。
- 扁平任务对象包含 `jobId`、源项目/主项目、目标名称、`status`、文件与字节总数/已完成数、失败摘要、成功结果及创建/开始/完成时间。状态为 `pending`、`running`、`succeeded` 或 `failed`。
- `GET /api/v1/project-copy-jobs/{jobId}` 返回调用者本人创建且当前仍有权查看源项目的单个任务。
- `GET /api/v1/project-groups/{groupId}/copy-jobs` 返回调用者在该主项目下当前可见的任务：所有进行中任务及最近 20 个终态任务。前端用该列表显示进度，并在新任务成功时刷新主项目子项目列表。
- 幂等范围是当前请求用户。相同用户以同一 `idempotencyKey`、源项目和目标名称重试时返回原任务；同一键换源项目或目标名称返回 409。网络结果未知时前端保留同一键重试并刷新任务列表。

## 执行、隔离与恢复

- `project_copy_jobs` 是持久化队列。提交事务写入 `pending` 后，即使客户端断开也完成数据库提交；关闭复制弹窗、刷新页面或退出当前页面不会取消任务。入队阶段只读取文件数量和字节数用于初始进度，不锁定全部文件行；worker 捕获与提交阶段才获取权威快照并复核。
- `ProjectCopyWorker` 默认开启并使用数据库命名锁，同一数据库在任一时刻只有一个 worker 领取任务，单 worker 串行执行。
- 每次取得数据库租约时递增 `project_copy_worker_state.epoch`；领取任务时把任务改为 `running`，同时记录该 worker epoch 并生成新的 32 位 execution token。候选文件只写入 `copy-jobs/{jobId}/{executionToken}/`，进度、提交和终态更新必须同时匹配任务 ID、`running` 状态、execution token 与 worker epoch，失去租约的旧 worker 不能覆盖或提交新执行。
- 进程重启或 worker 租约中断后，遗留的 `running` 任务恢复为 `pending`，文件/字节进度清零，旧 token 暂存目录清理；下一次领取使用新 token 从头执行。定期清理只移除既非当前执行、也未被文件记录引用的复制暂存目录。
- 可明确归类的业务或文件错误把任务置为 `failed` 并清理该次候选文件；进程停止或租约丢失会把任务退回 `pending`。
- （2026-09-28）执行阶段遇到 MySQL 死锁（1213）或锁等待超时（1205，含已映射为 409/40902 的同类错误）时，整次复制事务已回滚，任务清理候选文件后退回 `pending`，`retry_count` 加 1，并写入 `next_attempt_at`；worker 只领取 `next_attempt_at` 为空或已到期的任务。退避为 2s、4s、8s、16s、32s（上限 60s），最多重试 5 次，之后按普通错误置为 `failed`。其他错误不重试。成功提交后记录结果项目、复制履历和文件数，再清理未被引用的执行目录。

## 文件复制语义

- 只复制状态为 `AVAILABLE` 的文件。来源与目标各有独立文件记录，可以独立删除和下载；内容按 SHA-256 引用同一 `file_blobs` 实体，最后一个引用进入回收后才删除物理内容。
- 目标文件保留源文件的上传人、方向、原始文件名、扩展名、大小、MIME 和 SHA-256；复制操作者记录在项目复制记录和审计日志中，不冒充原上传人。
- 留言、留言图片、留言回执、通知查看记录、既有状态记录、邮件、上传会话及历史动态不复制。
- 目标子项目只产生本次 `COPY` 初始状态记录、复制动态和复制履历。

## 一致性与失败处理

- 执行前使用 checked 算术汇总源文件大小并检查存储卷剩余空间。
- 每个文件在引用前核对物理内容的实际字节数和 SHA-256。源文件缺失、路径异常、哈希缺失或不匹配时，整个复制失败；不会创建目标文件记录。
- 大文件复制采用两段短事务：第一段锁定并读取源项目、工令、文件和活动上传快照；事务外复制文件；第二段重新鉴权并精确核对源子项目、主项目当前元数据和工令、文件及活动上传。
- 快照期间发生任何变化都返回 409，并清理候选文件。
- 数据库提交结果无法确认时保留候选文件并返回可诊断错误，避免删除可能已被成功提交记录引用的文件。

## 履历与信息边界

- `GET /api/v1/projects/{id}/copy-history` 返回 `{ source, copies, hasRestrictedRelations }`。
- 来源和派生项目只有在调用者当前可见时才返回；不可见关系不披露项目 ID、名称或快照，仅将 `hasRestrictedRelations` 置为 `true`。
- `GET /api/v1/project-copies/{copyId}/files?page&pageSize` 分页返回文件映射；调用者必须同时可见来源和目标项目。
- 项目文件列表只返回 `isCopiedReference`，不泄露来源文件 ID。
- （2026-10-08 起）复制来源在派生副本存在期间不可删除，返回 409（“该子项目已被复制出副本，请先删除副本”）；副本本身若又被复制，也按来源处理。文件采用软删除，履历仍可显示复制时的文件名和当前删除状态。
- （2026-10-08 起）未开始（`DRAFT`）的副本可以删除：复制带入的文件不阻止删除，但复制之后新增的任何文件（含已软删）、留言或上传记录仍按普通规则返回 400。删除时在同一事务内移除复制履历（`file_copy_refs` 级联）、以该副本为结果的复制任务和复制带入的文件记录；共享内容按 SHA 命名锁在事务前加锁，失去最后一个引用的 blob 置为 `GC_PENDING`，由 `FilesMaintenanceService` 删除物理内容。审计 `PROJECT_DELETE` 额外记录 `copiedFromProjectId`、`copiedFromProjectName` 和 `copiedFileCount`。
- 已开始过的副本（如已终止）不享受上述豁免，复制带入的文件同样阻止删除。

## 审计与实时通知

- 审计动作是 `PROJECT_COPY`，目标为新子项目，详情包含来源/目标快照、文件数和总字节。
- 来源与目标分别生成不含对方名称的通用复制动态，避免负责人变更后通过历史摘要泄露不可见项目。
- 提交后向来源和目标项目的当前可见用户发布 `activity` 实时刷新事件。

## 数据库版本

- schema v7 引入 `project_copies` 和 `file_copy_refs`，保存项目名、文件名和复制操作者姓名快照，并通过外键防止履历悬空。
- 第 9 个 EF 迁移 `20260923141854_AddProjectCopyJobs` 引入 `project_copy_jobs` 与单行 `project_copy_worker_state`，包含请求人幂等唯一索引、队列领取索引、主项目/请求人/状态/时间列表索引，以及源项目、主项目、请求人和成功结果的外键；任务行保存 execution token 和 worker epoch。
- 升级必须显式执行 `--migrate-database`；非空数据库正常启动只验证迁移历史和结构，不自动升级。
