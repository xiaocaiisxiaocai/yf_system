# Robot 仿真协作流程调整方案

> 状态：**第 1 批已实施**（2026-10-31，核心流程 + 工作台待办），第 2、3 批待实施。实施完成后，本文对应条款取代 [主项目与子项目协作契约](主项目与子项目协作契约-2026-09-16.md) 的“状态与验收”“资料确认”、[邮件提醒规则契约](邮件提醒规则契约-2026-09-16.md) 的消息类型表，以及 [项目负责人转交与数据字典权限](项目负责人转交与数据字典权限-2026-09-23.md) 中“存在待验收子项目时禁止转交”的规定；`docs/公司与供应商协作平台-需求文档.md` §4、§6 同步改写。

## 1. 背景

2026-10-29 引入“资料确认”关卡后，一次正常交付需要：厂商上传 → 负责人资料确认 OK → 厂商提交 → 验收人（通常仍是负责人）验收通过。同一人对同一批资料判断两次，厂商多一次往返；驳回后还需重新确认未变化的资料。同时存在待办缺失、状态邮件缺失、逾期无提示等问题。本方案记录逐项讨论后的决定。

## 2. 决策汇总

| # | 议题 | 决定 |
|---|---|---|
| 1 | 两道内部关卡 | 合并为一关：负责人“资料确认 OK”即完成子项目；移除厂商“提交 / 撤回”与公司“验收通过 / 驳回” |
| 2 | 开始与资料交付 | 维持现状：先“开始”才能上传资料，草稿不传递资料，“开始”不检查资料是否齐备 |
| 3 | 草稿可见性 | 厂商可见草稿子项目，但草稿阶段**双方都不可留言** |
| 4 | 确认 / 退回 / 重开的执行人 | 仅子项目当前负责人本人，不需额外权限点 |
| 5 | 状态邮件 | 开始、终止、重新开始都发给厂商，各自独立开关 |
| 6 | 工作台 | 负责人“资料待确认”；厂商“已退回待补”“尚未回传”；列表可按资料状态筛选 |
| 7 | 误确认 | 允许负责人重开：等同事后退回，必填原因，业务资料重新跟随主项目，主项目回到进行中，邮件含开关，无时限 |
| 8 | 逾期 | 列表/详情逾期标示＋到期前 N 天（默认 3）与逾期当天各提醒一次，负责人与厂商各有开关 |
| 9 | 上传阻挡 | 只有厂商（S2C）的活动上传阻挡确认 / 退回 |
| 10 | 旧权限点 | 迁移退役 `project:submit`、`project:withdraw`、`project:confirm`，改写引用它们的检查，历史记录保留 |

## 3. 新工作流

| 当前状态 | 操作 | 下一状态 | 执行方和约束 |
|---|---|---|---|
| `DRAFT` | 开始 | `IN_PROGRESS` | 内部，需 `project:status`；厂商启用且至少一个启用厂商账号具备 `file:upload` |
| `IN_PROGRESS` | 资料确认 OK | `COMPLETED` | 仅当前负责人；资料状态为 `PENDING` 或 `RETURNED`；带 `expectedSupplierFileId`；无厂商活动上传 |
| `IN_PROGRESS` | 退回资料 | `IN_PROGRESS` | 仅当前负责人；资料状态为 `PENDING`；必填原因 1–500 字；带 `expectedSupplierFileId`；无厂商活动上传 |
| `COMPLETED` | 重开 | `IN_PROGRESS` | 仅当前负责人；必填原因 1–500 字；带 `expectedUpdatedAt`（实施时取消“主项目未终止”限制，见 §11） |
| `IN_PROGRESS` | 终止 | `TERMINATED` | 内部，需 `project:status`；无活动上传 |
| `TERMINATED` | 重新开始 | `IN_PROGRESS` | 同“开始”的厂商前提 |

`PENDING_CONFIRMATION` 状态退出模型（见 §9 存量数据处理）。

### 3.1 资料状态（仅 `IN_PROGRESS` 返回）

| 值 | 含义 |
|---|---|
| `NO_MATERIAL` | 尚无可用的 S2C 文件 |
| `PENDING` | 有 S2C 文件，待负责人确认 |
| `RETURNED` | 已退回，`materialReviewReason` 为原因；厂商再上传后回到 `PENDING` |

`APPROVED` 不再作为进行中的状态出现：确认 OK 即完成。退回结果仍绑定当时最新的 S2C 文件 ID，新上传使其失效回到 `PENDING`（沿用现有 `EffectiveMaterialReview` 逻辑）。任何状态流转仍清空资料确认字段。

### 3.2 资料确认 OK（完成）

- 在同一事务内：项目改为 `COMPLETED`、写状态历史（动作名建议 `MATERIAL_APPROVE`，替代 `CONFIRM`）、审计 `PROJECT_MATERIAL_APPROVE`、按 `allowCompletion: true` 重算主项目（全部完成则自动完成）。
- 完成时冻结业务快照的现有规则不变。
- 前端确认框写明后果（“确认后子项目将完成并冻结”），并列出本次涵盖的 S2C 文件数与最新文件名。
- 通知厂商：沿用 `PROJECT_MATERIAL_APPROVED` 事件，正文改为“回传资料已确认 OK，子项目已完成”。

### 3.3 重开

- 子项目回到 `IN_PROGRESS`，资料状态写为 `RETURNED`，`material_review_file_id` 为当前最新 S2C 文件，`material_review_reason` 为重开原因；厂商看到与普通退回一致的提示。
- 业务资料按“未完成子项目”处理：重新同步主项目当前公共资料（工令号、机型、料号、型号、Robot 负责人、优先级、需求完成时间等），不再保留完成时快照（状态历史与审计已留痕）。
- 主项目重算状态：因该子项目完成而自动完成的主项目回到进行中；清空主项目完成时间。
- 状态历史动作 `REOPEN`，审计 `PROJECT_REOPEN`，项目动态“重开子项目”，计入协作通知。
- 邮件 `PROJECT_REOPENED` 发给厂商全部启用联络人，开关 `notify.event.project_reopened`。
- 请求 `POST /api/v1/projects/{id}/reopen`，体 `{ expectedUpdatedAt, reason }`。

### 3.4 草稿阶段

- 厂商可见草稿子项目（列表、详情、主项目），但草稿阶段内部和厂商都不能发留言（`EnsureWritable` 增加 `DRAFT`），提示“项目尚未开始，暂不能留言”。
- 上传规则不变：仅 `IN_PROGRESS` 可上传。

### 3.5 负责人转交

- 移除“存在待验收子项目时禁止转交”的限制（该状态已不存在），任意状态均可转交。
- 负责人请假时通过转交让他人执行确认。

## 4. 权限点退役（决策 10）

- 新迁移从权限目录、角色授权中删除 `project:submit`、`project:withdraw`、`project:confirm`；`BootstrapSeedCatalog` 同步删除。
- `RoleService.SupplierPermissionCodes` 由 8 项减为 6 项；“供应商角色授权上限”中对 submit/withdraw 的豁免条款随之删除。
- “开始 / 重新开始”的厂商前提第 3 条改为：启用账号中至少一个通过启用角色具备 `file:upload`，提示“项目所属厂商的启用用户都没有上传文件权限……”。
- 厂商取消同供应商上传会话：只需 `file:upload`（原为 `file:upload` + `project:submit`）。
- `ProjectReviewerService`、`CanReceivePendingAcceptance`、待验收邮件（`EnqueuePendingAcceptanceAsync` 及其取消逻辑）删除。
- 历史状态历史（`SUBMIT`/`CONFIRM`/`REJECT`/`WITHDRAW`）、审计和项目动态保留，前端动态文案映射保留以正常显示。

## 5. 邮件提醒（决策 5、7、8）

### 5.1 新增消息类型开关

| 参数 | 默认 | 事件 | 收件人 |
|---|---|---|---|
| `notify.event.project_started` | `true` | `PROJECT_STARTED` 开始 | 厂商全部启用联络人（无联络人时账号邮箱） |
| `notify.event.project_terminated` | `true` | `PROJECT_TERMINATED` 终止 | 同上 |
| `notify.event.project_restarted` | `true` | `PROJECT_RESTARTED` 重新开始 | 同上 |
| `notify.event.project_reopened` | `true` | `PROJECT_REOPENED` 重开 | 同上 |
| `notify.event.project_due_soon` | `true` | `PROJECT_DUE_SOON` 即将到期 | 见 5.2 |
| `notify.event.project_overdue` | `true` | `PROJECT_OVERDUE` 已逾期 | 见 5.2 |
| `notify.due.internal.enabled` | `true` | 到期/逾期是否发给负责人 | — |
| `notify.due.supplier.enabled` | `true` | 到期/逾期是否发给厂商 | — |
| `notify.due.remind_days_before` | `3` | 提前天数，范围 1–30 | — |

- 仍受总开关 `notify.enabled` 与对象开关 `notify.internal.enabled` / `notify.supplier.enabled` 约束。
- 退役 `notify.event.project_submitted` / `project_confirmed` / `project_rejected` / `project_withdrawn`（迁移删除配置行，前端“邮件提醒规则”同步调整）。`notify.event.project_material_reviewed` 保留，涵盖确认 OK（完成）与退回。
- 迁移以 `INSERT IGNORE` 补齐新参数，且不放入 `BootstrapSeedCatalog`（避免首启重复键），`Down` 不删除以保持往返参考数据一致（遵循 CLAUDE.md 迁移约定）。

### 5.2 到期提醒

- 新后台服务每天扫描一次（单实例，数据库时钟），对象为 `IN_PROGRESS` 子项目（`DRAFT` 尚未交付、终态不提醒）。
- 需求完成时间前 `remind_days_before` 天发 `PROJECT_DUE_SOON` 一次；逾期当天（日期已过）发 `PROJECT_OVERDUE` 一次；之后不重复。
- 去重键：`due:{kind}:{projectId}:{expectedCompletionDate}`，修改需求完成时间后按新日期重新计算；同一日期同一类型只发一次。
- 收件人：负责人（`notify.due.internal.enabled`）与厂商全部启用联络人（`notify.due.supplier.enabled`），复用现有收件资格复核与 outbox 流程。

## 6. 工作台与列表（决策 6、8）

- 负责人待办：本人负责、`IN_PROGRESS` 且资料状态 `PENDING` 的子项目（“资料待确认”）。
- 厂商待办：`IN_PROGRESS` 且资料状态 `RETURNED`（“已退回待补”）或 `NO_MATERIAL`（“尚未回传”）。
- `DashboardSummaryResponse.pendingConfirmations` 与 `GET /dashboard/pending-projects` 改为上述语义（字段改名需同步 OpenAPI 与前端类型）；主项目列表的待验收计数改为资料待确认计数。
- 子项目 / 主项目列表新增筛选：资料状态（未回传 / 待确认 / 已退回）、是否逾期。
- 逾期标示：未完成（`DRAFT`/`IN_PROGRESS`）且需求完成时间早于今天时，列表与详情显示“逾期 N 天”。

## 7. 上传阻挡（决策 9）

资料确认 / 退回只统计厂商发起（`S2C`）的阻挡中上传会话；内部 C2S 上传不阻挡。终止仍统计全部活动上传。

## 9. 存量数据处理（已确认并实施）

开发阶段不要求兼容旧 schema 数据，但开发库升级时仍需处理状态为 `PENDING_CONFIRMATION` 的子项目。建议迁移将其改为 `IN_PROGRESS`、资料确认字段清空（即资料状态 `PENDING`），负责人随后直接确认 OK 完成；同时取消对应的待验收邮件（`PROJECT_SUBMITTED` 的 `PENDING` 记录改为 `CANCELLED`）。如需其他处理方式，在第 1 批实施前确定。

## 11. 实施记录（第 1 批，2026-10-31）

- 重开未加“主项目已终止时不能重开”的限制：主项目状态由子项目汇总（如 {A 已完成, B 已终止} 时主项目为已终止），已终止的子项目同样可以重新开始；若禁止重开，该场景下 A 无法返工，与“重新开始”不一致。重开后主项目按规则重算为进行中。
- 工作台待办的新语义提前到第 1 批：原待验收统计依赖已退役的 `project:confirm`。内部待办为“本人负责且资料待确认”，厂商待办为“资料已退回”和“尚未回传”；接口字段 `pendingConfirmations` → `pendingTasks`，待办列表项返回 `materialReviewStatus`。主项目 `pendingCount` → `materialPendingCount`。
- 迁移 `RetireAcceptanceWorkflow` 的 `Down` 只恢复 `projects.confirm_side` 列，不恢复已退役的权限点与授权（与其他目录迁移一致，保持往返参考数据不变）。
- 遗留在途的 `PROJECT_SUBMITTED` 邮件在发送前取消（审计 `EMAIL_CANCELLED_STALE`，reason `PROJECT_ACCEPTANCE_RETIRED`）。
- 重开邮件与开关、草稿禁言随第 2 批实施。
