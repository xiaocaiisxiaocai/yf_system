# OEM module

separate business line (company ↔ OEM vendor file transfer with approval), composed in `Modules/Oem/OemModule.cs` from feature-slice folders (Common, Data, Storage, Identity, Admin, Policies, Approval, Transfers, Uploads, Validation, Delivery, Maintenance, Notifications). Routes live under `/api/v1/oem` (SPA: internal `/oem`, vendor portal `/oem-portal`). It has its own realm via `IRealmIdentityExtension`: internal staff reuse the main identity cache/sessions, collaboration supplier accounts cannot enter OEM, and OEM tokens cannot reach the collaboration API. Writes go through `OemUnitOfWork` (EF transaction + DB-clock `Now` + events dispatched after commit) rather than the `AccessService` request/write pattern described in the repository-root `CLAUDE.md`. File bytes live only under `App:OemStorageRoot` (`uploads/` → `quarantine/` → `available/`, atomic move), never in collaboration storage/blobs; an empty `OemStorageRoot` leaves OEM file endpoints reporting "unconfigured" while the rest of the app runs. Background jobs (validate, promote, purge, reconcile, expiry…) run in `OemBackgroundWorker`. "VALID" means integrity and format (leading bytes match the extension, not an executable) checks passed; since 2026-11-13 archives and Office documents are never opened — never describe it as a virus scan.

- Visibility (`TransferAccess`): built-in 系统管理员 holders (with `oem:transfer_view`) and internal accounts whose ODM/OEMA data range is ALL see every transfer; the range is set by an administrator per user or as the role default (`DataScopeService`, `role_data_scopes`/`user_data_scopes`), not by a permission code. Other internal staff see their own, those they approve, and inbound ones the vendor chose to notify them about; an ORG range (own organisation and below, which is also what an organisation leader gets by default) also shows what the people it covers sent or were notified about — that includes the organisation the account belongs to, not only the organisations it leads. Vendor sends of inbound transfers must be signed (always required) with a freely typed person name of that vendor (`signer_name`, no contact id).
- Vendor responses mask internal employee numbers; for an internal sender, the vendor-facing `sender.employeeNo` is empty. Completed approval statuses are projected as approved.
- OEM companies, shared accounts and contacts are separate directory records. A company contains only name, remark and status; the `RemoveOemCompanyPrimaryContact` migration directly drops the legacy company contact name/phone/email and contact phone columns and deliberately does not create contact records from them. A shared account accepts only account plus initial password and has no operator name/email in the request or response. Contacts contain name, required notification email, order and status; multiple active contacts per company are expected. `oem:directory_view` is a read-only grant over companies and accounts only — contact e-mail addresses stay behind `oem:company_manage`, and the migration never backfills this code onto existing roles (it is only granted explicitly, or to the built-in administrator).
- Since 2026-11-17 the outsourcing list (外协清单) uses OEM companies and contacts as its vendors and mail recipients (read only there). `DeleteCompanyAsync` refuses a company referenced by outsourcing items, type mappings or mails; disable it instead. Vendor accounts read their company's outsourcing records, read only, at `GET /api/v1/oem/outsource-items` (portal page `/oem-portal/outsource`, served by `Outsource/OutsourceVendorView.cs`); internal actors get 403 there.
- The company directory provides create-only XLSX imports and exports for company masters, accounts and contacts. Child sheets repeat the vendor name on each row, so a pre-existing company can receive accounts or contacts without re-importing the master; duplicate keys are skipped, credentials are never exported, and every new account is active with first-login password change required. Password validation is the repository-wide 5–20-character policy.
- OEM mail uses the shared SMTP/outbox infrastructure with independent `oem.notify.*` total/event switches. Vendor recipients are all active contacts with valid email addresses, deduplicated by address; account `RealName`/`Email` compatibility fields are not recipient data. No active contact means no vendor mail. Inbound (OEM → internal) release mail goes only to the people the vendor chose at send time (`oem_transfer_internal_recipients`) from the one notification list shared by every vendor: by default every internal staff member with ODM/OEMA view + download except system administrators (they see every transfer and are never mailed about vendor files), minus people an administrator removed (`oem_internal_recipient_exclusions`, managed under 厂商与账号 with a re-import dialog). Queued mail rechecks the OEM rule, company/account/business state and current contacts immediately before delivery, and transient delivery failures retain the outbox row for the shared mail worker's bounded retry path.
- The system settings `邮件提醒规则` tab embeds the same `OemMailRulesPanel` used by OEM settings, so both entry points edit the same OEM keys. SMTP connection settings remain global and shared with Robot; only notification policies are business-specific.
- OEM login checks the source IP bucket before lookup, then rate-limits the IP plus resolved account ID and account-wide ID. Unknown names use normalized text for the account bucket and receive the same throttled response.
- Per account and minute, each with its own budget: preview 120 calls, download-start and upload-init 60 calls each, matching collaboration transfers (`429/42902`). Download streams re-check the account and session every five seconds and count bytes only after a successful response flush.
- Validation jobs rotate by vendor and cap each vendor at 100 unfinished jobs. Reconciliation pauses and emits `OEM_RECONCILE_STORAGE_SUSPECT` if the root is unreadable or mass loss is suspected. A matching file may have its payload status restored from `STORAGE_LOST`; its transfer lifecycle remains terminal and the cancelled approval instance is not reopened by the recovery inbox.
