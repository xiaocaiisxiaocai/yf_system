# 公司与供应商协作平台 - 需求文档

**版本**：V2.1
**更新日期**：2026-09-23
**状态**：主项目／子项目协作契约

## 1. 目标与范围

平台服务一家公司的内部团队与外部供应商企业，提供项目资料交换、留言讨论、交付提交、公司验收和全过程留痕。维护入口是 `server_dotnet` 的 ASP.NET Core .NET 8 API，接口前缀为 `/api/v1`；早期的 Rust 原型（`yf_server`）已从仓库移除，不作为运行、测试或升级依赖。

平台不是多租户 SaaS。公司管理员创建和维护供应商企业及其账号；文件存放在服务端私有磁盘，通过认证接口访问。

## 2. 业务对象和数据边界

### 2.1 主项目与子项目

主项目（`project_group`）是资料归集和公共信息的容器。每个主项目只关联一个供应商企业，并且创建时至少同时创建一个子项目（`project`）。主项目维护：

- 主项目名称和说明；
- Robot 厂商（即供应商企业）；
- 工令号、机型、料号和型号；
- 自动绑定创建人的公司内部负责人及其课别；
- 优先级和需求完成时间。

Robot 料号按厂商过滤，选定料号自动带出型号，后端同时验证归属。初始化按用户提供的六轴手臂 Excel 导入 7 个品牌、27 个料号，品牌映射供应商，SAP 品名规格映射型号；不再维护独立厂商字典。详见 [Robot 料号与创建人负责制](../server_dotnet/docs/Robot料号与创建人负责制-2026-09-23.md)。

子项目维护自己的名称和说明，拥有独立的文件、留言、动态、提交记录和验收状态。公共信息从主项目继承；主项目业务资料变更只同步到尚未完成的子项目，已经验收完成的子项目保留验收时的业务资料。负责人和课别决定访问权，始终跟随主项目同步到全部子项目，包括已完成子项目。

主项目状态由子项目汇总：全部子项目完成时自动完成；全部子项目都已结束且至少一个被终止时自动终止；新增或重启未完成子项目时主项目重新进入进行中。主项目状态不是人工绕过子项目状态的第二条审批流。

### 2.2 供应商企业共享范围

供应商企业是外部协作主体。同一供应商企业可以拥有多个启用账号，这些账号共享该企业名下全部主项目、子项目、文件和留言权限；供应商 A 永远不能访问供应商 B 的数据。当前授权粒度是供应商企业，后续若需按联系人或部门隔离，应新增明确的项目外部联系人关系，不能用前端隐藏代替权限。

### 2.3 内部单负责人范围

项目只设置一个当前内部负责人，不再使用项目成员、成员选择器或 `project_members` 表。普通内部用户只能访问自己负责或自己创建的主项目及其子项目；拥有 `project:view_all` 的内部管理员可查看全部项目，但仍需单独的操作权限才能执行状态、验收或管理操作。

新主项目的负责人由服务端绑定当前创建人，必须是启用且拥有 `project:list`、`project:create` 的内部用户。有效直属课别自动带出，未设置课别时也允许创建。编辑公共资料不改变负责人，子项目继承主项目负责人；旧项目保留原有负责人，不追溯重写归属。

负责人仍负责未结束主项目时，禁止停用、改为供应商或撤销必要的项目权限；账号被任一项目或历史记录引用时不能删除。项目资料编辑不转交负责人；拥有 `project:transfer` 的内部用户可通过专用操作变更主项目负责人（存在待验收子项目时除外），规则见[项目负责人转交与数据字典权限](../server_dotnet/docs/项目负责人转交与数据字典权限-2026-09-23.md)。

## 3. 身份和权限

| 身份 | 数据范围 | 主要能力 |
|---|---|---|
| 系统管理员 | 全部主项目和子项目 | 组织、账号、角色、供应商、项目和系统管理 |
| 项目管理员 | 通过 `project:view_all` 查看全部项目 | 项目维护、状态管理、负责人转交、验收，具体能力仍由权限点控制；内部账号不能提交或撤回验收 |
| 内部负责人 | 自己负责或自己创建的主项目及其子项目 | 查看、上传、留言、状态操作和公司验收，具体能力仍由权限点控制 |
| 供应商账号 | 所属供应商企业的全部项目 | 查看、上传、留言、下载和提交内部验收 |

关键权限独立存在：`project:list`、`project:create`、`project:update`、`project:status`、`project:submit`、`project:confirm`、`project:withdraw`、`project:view_all` 和 `project:transfer`（变更项目负责人）。数据字典维护使用独立的 `dict:manage`。服务端同时执行身份、权限和项目数据范围校验。

## 4. 子项目工作流

| 当前状态 | 操作 | 下一状态 | 执行方和约束 |
|---|---|---|---|
| `DRAFT` | 开始 | `IN_PROGRESS` | 仅内部用户，需 `project:status`；所属厂商至少有一个启用的供应商账号 |
| `IN_PROGRESS` | 提交内部验收 | `PENDING_CONFIRMATION` | 仅供应商账号，需 `project:submit`；至少一个可用文件且没有活跃上传 |
| `PENDING_CONFIRMATION` | 通过 | `COMPLETED` | 仅内部用户，需 `project:confirm`，并且必须是当前有效验收申请的验收人 |
| `PENDING_CONFIRMATION` | 驳回 | `IN_PROGRESS` | 仅内部用户，需 `project:confirm`，必须填写驳回原因 |
| `PENDING_CONFIRMATION` | 撤回 | `IN_PROGRESS` | 仅提交当前申请的供应商账号，需 `project:withdraw`；内部账号不能撤回 |
| `IN_PROGRESS` | 终止 | `TERMINATED` | 仅内部用户，需 `project:status` |
| `TERMINATED` | 重启 | `IN_PROGRESS` | 仅内部用户，需 `project:status`；所属厂商至少有一个启用的供应商账号 |

公司内部验收是唯一验收边界。内部账号提交交付申请应被拒绝；供应商账号提交后，由启用且具有 `project:list`、`project:confirm` 的内部人员确认／驳回，且该人员必须是当前负责人、主项目创建人或具有 `project:view_all`。提交、确认、驳回、撤回都必须携带当前申请版本，过期版本返回冲突，不能误操作新申请。

`PENDING_CONFIRMATION` 冻结该子项目的资料编辑、文件上传删除和其他业务写入，但继续允许双方留言。`COMPLETED` 是只读终态，文件和留言仍可查看、下载及查看回执；`TERMINATED` 只有内部重启状态操作可写。主项目编辑遇到待验收子项目时必须阻止保存；已完成子项目的业务资料和工令号在验收后冻结，负责人和课别仍保留主项目公共归属。

## 5. 文件和留言

文件和留言只归属于子项目，不直接归属于主项目。文件方向由认证身份推导：内部上传为“公司 → 供应商”（`C2S`），供应商上传为“供应商 → 公司”（`S2C`），客户端不能任意选择方向。下载、预览、分片上传、合并和批量下载都必须经过项目范围校验。

双方可以在可见子项目中留言。留言按时间线展示，记录发送人和时间。待验收阶段仍可留言；完成或终止后禁止新增留言。每条留言的已读回执按用户记录，删除留言后正文和目标状态不应从通知中泄漏。

## 6. 通知与已读口径

系统保留两套互不替代的状态：

- 协作通知／顶部铃铛使用 `project_activities` 和 `collaboration_reads`，表示某条项目动态是否被用户查看；动态可以是文件、留言或工作流事件。
- 项目留言的“已读 x/y”使用 `messages` 和 `message_reads`，表示留言正文是否被每个可见协作方读到。

因此铃铛清零并不代表留言正文已读，项目未读留言数也不等于通知数。接口、页面和验收脚本必须分别展示这两个口径，不能用一个状态覆盖另一个状态。

通知规则如下：

- 供应商上传文件或留言，通知该子项目当前负责人；
- 内部上传文件或留言，通知该供应商企业全部启用且具备项目列表权限的账号；
- 供应商提交内部验收，通知当前负责人及具备 `project:view_all`、`project:list`、`project:confirm` 的启用内部验收人；
- 公司通过、驳回或撤回，通知最近提交的供应商账号，撤回还通知待验收的可见协作方；
- outbox 入队与业务状态变更在同一事务内完成，邮件发送由异步 worker 负责；
- 收件人按当前有效账号和项目范围去重，禁用账号不再收到新通知。

## 7. API 入口约定

主项目创建和查询使用：

- `POST /api/v1/project-groups`：创建主项目，同时用 `subprojectNames` 创建一个或多个子项目；请求必须包含 `supplierId`、`robotPartId` 及其他公共元数据；负责人由认证身份确定，不能由客户端指定；
- `GET /api/v1/project-groups`：按主项目分页、筛选；
- `GET /api/v1/project-groups/{id}`：返回主项目和 `projects` 子项目列表；
- `PUT /api/v1/project-groups/{id}`：业务资料同步到未完成子项目；供应商和负责人保持不变；
- `POST /api/v1/project-groups/{id}/projects`：在未结束主项目下新增子项目。

子项目协作和验收使用 `/api/v1/projects/{id}` 下的详情、状态、文件、留言、提交、确认、驳回和撤回接口。`/api/v1/projects` 不再作为主项目创建入口，也不存在项目成员写入流程。

## 8. 追溯、安全和验收

关键操作必须写入审计和项目动态：主项目及子项目创建、公共资料同步、开始、终止、重启、供应商提交、公司确认／驳回／撤回、文件、留言、回执、账号和权限变化。料号目录维护也须写入审计。审计不能记录密码、磁盘真实路径或不必要的网络细节。

文件使用 UUID 等不可猜测名称落盘，临时上传目录完成校验后原子落地；下载和预览使用认证接口并防止路径遍历。状态转换使用事务和并发版本校验，重复提交、过期确认、并发文件删除和活跃上传都必须返回明确错误且不留下部分业务写入。

当前 .NET 数据库以 EF Core 迁移历史为版本依据，包含主项目／子项目关系、料号目录、公共元数据、负责人完整性约束、旧成员模型清理和独立邮件提醒规则。隔离 HTTP 回归必须创建随机 `yf_test_dotnet_*` 数据库和临时存储，验证结束只删除自己创建的资源。

## 9. 已确认决策

| 决策点 | 当前结论 |
|---|---|
| 协作层级 | 主项目归集公共资料，子项目独立协作和验收 |
| 供应商范围 | 一个主项目只关联一个供应商企业；该企业启用账号共享项目范围 |
| 内部范围 | 单一当前负责人；管理员可全局查看；无项目成员模型 |
| 提交和验收 | 供应商提交，内部负责人或授权内部验收人确认／驳回 |
| 完成保护 | 已完成子项目业务内容、元数据和工令号冻结；负责人和课别保留主项目公共归属 |
| 负责人绑定 | 新主项目由创建人负责；编辑不转交；被历史引用的账号不能删除 |
| 已读状态 | 协作动态通知与留言正文回执分开统计、分开展示 |
| 文件方向 | 服务端按内部／供应商身份自动推导 |
| 存储 | 私有本地磁盘，认证接口下载和预览 |
| 账号体系 | 独立工号密码账号，供应商账号由公司管理员维护 |
