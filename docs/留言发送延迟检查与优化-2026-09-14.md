# 留言发送延迟检查与优化

日期：2026-09-14。基线：`2477d91`，已包含 main 的 SignalR 实现 `84af9bf`。

## 结论

确认存在前端重复刷新和不必要的列表加载遮罩；发送流程没有固定等待一秒的逻辑。SignalR 的一秒初始退避用于连接失败后的重试，与正常发送不同。

本次隔离测量未复现“发送一条需要一秒多”。不能据此认定用户当时的网络、浏览器会话或数据库写入也同样快。电脑操控工具本轮未能连接到用户浏览器，因此没有获取用户当时的请求瀑布或实时连接状态。

## 已确认的问题及处理

- `MessagePanel` 原来丢弃发送接口返回的完整留言，再请求首屏；按钮恢复后，列表还要等待 GET，并显示整块加载遮罩。现在直接展示服务器确认提交的响应，保留已加载历史，不提前假定发送成功。
- 一次消息推送先改变 `liveMessages`，随后通知摘要又改变 `activityRevision`，两次使同一列表失效。现在实时连接正常时使用推送版本；断线时继续使用摘要轮询，重连后仍补查。
- 原定位留言视图发送后先拉旧定位，再退出定位拉全列表。现在交由退出定位后的作用域更新加载一次。
- 发送期间的新草稿不会被旧发送完成清空；同步/分页旧响应不得覆盖已确认留言；快速重复点击只提交一次。推送先到时按留言 ID 去重。
- 已有留言时后台加载不再遮住整个列表。

未修改 SignalR 协议、后端事务、权限检查、邮件队列或真实业务数据。

## 分段测量

工具：Playwright、已安装的 Chrome、浏览器请求/响应事件、SignalR `ProjectChanged` 帧、DOM MutationObserver；真实 ASP.NET Core API 和专用 MySQL 临时库。使用两个独立浏览器上下文分别登录管理员和供应商。所有留言只写入测试夹具创建的临时项目，测试库随夹具清理。

每组连续发送 8 条；“点击”起点包含 Playwright 点击调度时间，“显示”指 DOM 插入时间，不是人的视觉感知计时。请求日志仅保留方法、路径、状态、时间，不记录令牌、查询凭据、密码或业务正文。

| 指标 | 修复前构建版 | 修复后构建版 |
| --- | ---: | ---: |
| 发送者每条留言触发的列表 GET（稳态 7 条） | 3 | 1 |
| 接收者每条留言触发的列表 GET（稳态 7 条） | 2 | 1 |
| POST 响应后到发送者 DOM 更新，中位数 | 16 ms | 6.5 ms |
| 点击到发送者 DOM 更新，范围 | 68–83 ms | 58–93 ms |
| 点击到接收者 DOM 更新，范围 | 78–101 ms | 104–140 ms |

这两组是先后执行的小样本，接收侧耗时有波动，不能声称接收侧端到端耗时下降。确定的收益是减少列表请求，并移除发送者显示所依赖的第二次 HTTP 往返。

另外使用当前 5173 的 Vite 开发资源连接隔离测试 API，8 条样本测得：发送者 68–92 ms、接收者 125–152 ms。这里只转送前端静态开发资源，业务 API 和账号仍来自隔离夹具；不代表直接测量了真实开发数据库上的业务留言。

- 浏览器回执/重连证据：`.runlogs/message-latency-20260914/browser-live-results.json`。初轮有异步断言失败，脚本改为在有界时间内等待精确回执帧及重连握手后重验；未通过延长业务计时来声称性能提升。

若真实页面仍出现一秒以上延迟，后续应对那一次操作采集 POST 耗时、连接状态、推送到达时间与列表 GET 耗时，进一步区分接口慢、重连补查和浏览器渲染，不能仅凭 SignalR 已启用断言原因。
