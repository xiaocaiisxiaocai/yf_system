# 留言已读回执同步修复

## 问题与原因

供应商阅读留言后，其页面会写入已读记录并刷新本人的回执；发送者页面的计数仍停留在首次加载结果。项目活动版本只反映活动事件，不包含他人的 `message_reads` 变化，所以仅依赖协作信息更新提示无法同步回执。

只读核对当前开发数据库：项目 1、留言 1 已存在 1 条已读记录。未修改该数据。

## 修复

- 新增 `GET /api/v1/projects/{id}/message-receipts?ids=1,2`，只返回回执计数，不返回留言正文。校验项目访问权限，只包含当前项目未删除的留言，最多 500 个去重后的正整数 ID。
- 批量接口与原留言列表共用计数逻辑，继续排除发送者，以当前项目参与人为分母。
- 留言页可见时每 5 秒查询当前视口中的留言，独立更新人数，不重新加载列表、不清空草稿、不重置历史游标。
- 切回窗口或联网后立即同步；隐藏、离线或离开留言页时暂停；卸载或切换项目时取消请求并拒绝迟到结果。网络失败保留上次计数并逐步退避，最长 60 秒。
- 打开的回执详情、已读名单同步刷新；手动打开回执时也更新行内人数。

## 验证

- 后端 170/170 测试通过，无跳过。新增真实隔离 MySQL 测试涵盖供应商写已读后管理员计数 0→1、分母一致、发送者排除、跨项目过滤、无权限拒绝及 ID 参数限制。
- 前端 157/157 测试通过。新增回归涵盖草稿/历史列表保留、只同步可见消息、隐藏恢复、active 清理、旧项目响应失效和失败恢复。
- TypeScript/Vite 与 .NET 构建通过。
- 两个隔离浏览器身份在真实前端上使用共享模拟接口状态：供应商读后，管理员约 4.0 秒由 0/2 自动变为 1/2，已打开的详情同步更新；草稿保留，无额外留言列表请求。UI 证据与隔离数据库服务测试分别验证，不冒称写入了真实业务测试数据。
