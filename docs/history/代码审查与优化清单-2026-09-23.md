### 状态说明

- **待核对**：等待实现报告，或尚未完成源码与定向证据复核。
- **已修复**：源码已落实方案，并有与该项风险相称的定向检查；整体验证结果另行记录。
- **已实现，待整体验证**：已复核源码和回归用例，但最终统一门禁尚未结束。
- **部分完成**：已完成不改变既有业务契约的部分，仍有明确后续决定或跨端工作。
- **原已具备或不适用**：复核后确认原判断不成立、现有实现已覆盖，或建议不适用于当前契约；必须写明依据。
- **保留现有契约**：属于明确业务/架构取舍，未按原建议修改；必须写明风险边界。
- **待环境验证**：代码或脚本已完成，但必须在 MySQL、IIS、反向代理或其他目标环境中验证。

## 二、并发与锁（影响全系统吞吐）

### Identity-M2 密码哈希在排他管理锁内执行 [已核实]
- 位置：`IdentityService.cs:191-201`（改密：Argon2 校验+哈希）、`UserService.cs:73`/`:201`、`SupplierService.cs:179`/`:247`。
- 问题：`GateAsync` → `LockManagementAsync`（`security.management_lock` FOR UPDATE）之后才 `PasswordService.HashAsync`。所有业务写入都要拿该行的共享锁。Argon2 常规数十毫秒，而 `PasswordService` 并发槽满时会排队最长 15s。
- 场景：登录高峰占满哈希槽 → 管理员重置一个密码 → 事务内等待 15s → 全系统项目/文件/消息写入排队 → 大量 409/40902。
- 建议：事务外先哈希；改密先在锁外校验旧密码，锁内重读哈希未变再写入（登录已采用这个模式）。

### Identity-M3 Token 刷新与登出获取排他锁 [已核实]
- 位置：`IdentityService.cs:114`（RefreshAsync）、`:173`（LogoutAsync）。
- 问题：每个客户端约 30 分钟刷新一次，每次都要等待所有进行中的业务事务结束并阻塞新事务。
- 建议：改用 `LockBusinessAsync`（共享）+ 现有 users / refresh_tokens 行级 FOR UPDATE；权限变更本来就会 bump identity revision。

### Data-M2 共享/排他闸门的排队放大 [已核实锁语义，概率待确认]
- 位置：`Infrastructure/AppDb.cs`（LockBusinessAsync / LockManagementAsync）。
- 场景：A 持 S 锁做慢事务 → 管理员 B 请求 X 锁等待 → InnoDB 让所有后续 S 请求排在 B 后面 → 全系统业务写入阻塞到 A 提交。
- 建议：缩短业务事务（通知参与者解析、审计目标查找移到拿闸门之前）；仅对 LockManagementAsync 设置较短的会话级 `innodb_lock_wait_timeout`（如 5s）快速失败；给闸门加事务耗时埋点。

### Projects-M1 复制入队锁住源项目所有文件行 [已核实]

### Files-M1 分块重传在行锁内重算最多 64 MiB 哈希 [已核实]

## 三、数据正确性

### Data-H3 DB 默认时间戳使用会话时区，应用按 UTC 读取 [已核实代码；实际偏差取决于 MySQL time_zone]
- 位置：
  - 实体配置 `HasDefaultValueSql("CURRENT_TIMESTAMP")` + `ValueGeneratedOnAddOrUpdate`：`AdminEntities.cs:77-117`、`IdentityEntities.cs:63-87`、`FileEntities.cs:82-116`、`MessageEntities.cs:51-92`、`ProjectEntities.cs:171-246` 等。
  - `AppDb.cs:42` 连接串 `DateTimeKind = Utc`；全仓库没有 `SET time_zone` / `SessionVariables`。
- 未显式赋值的写入：新建 Supplier（`SupplierService.cs:55`）、Department（`DepartmentService.cs:65`）、User（`UserService.cs:71`、`SupplierService.cs:177`）、ProjectGroup（`ProjectGroupService.cs:98`）；不设 UpdatedAt 的 `ExecuteUpdate`（`UserService.cs:180,202`、`SupplierService.cs:61,83,208,231`、`RoleService.cs:89,123`）依赖 `ON UPDATE CURRENT_TIMESTAMP`。代码中 `ProjectCopyService.cs:~300` 注释已承认“CURRENT_TIMESTAMP may use server local time”。
- 场景：MySQL `time_zone=SYSTEM` 且服务器为 UTC+8 时，这些列被当作 UTC 读取后偏 8 小时，与 DbClock 写入的 UTC 列混排/比较出错（例如“创建时间晚于更新时间”）。

### Data-M3 三张表 collation 与其他表不一致 [已核实]
