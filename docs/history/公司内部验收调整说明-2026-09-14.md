# 公司内部验收调整说明

## 业务规则

验收结论由公司内部人员作出，供应商不负责确认或驳回项目。

| 操作 | 权限与条件 | 结果 |
| --- | --- | --- |
| 提交内部验收 | 具备项目访问权限与 `project:submit`；项目进行中，至少一个可用文件，无活动上传会话 | 进入待内部验收，确认方固定 `COMPANY` |
| 确认通过／驳回 | 内部账号，具备项目访问权限与 `project:confirm`；项目待内部验收 | 通过后完成；驳回后回到进行中，并保留驳回原因 |
| 撤回申请 | 具备 `project:withdraw`，并满足原有提交人／内部管理范围限制 | 回到进行中 |

内部人员与供应商账号均可在获得提交权限后发起申请。角色名称不代替账号类型和项目范围检查。供应商即使携带遗留的 `project:confirm` 授权，也不能调用确认或驳回接口。当前业务未要求提交人与验收人必须不同，因此不额外增加二人分离限制。

新申请只能使用 `confirmSide: "COMPANY"`，省略时也按公司内部处理；显式请求 `SUPPLIER` 会被拒绝。前端按钮、工作台待办、协作通知与接口摘要均按内部验收展示。

## 权限配置

供应商角色允许工作台、项目列表、上传／下载／预览文件、发表留言，以及按职责配置的提交／撤回验收权限，不再允许确认／驳回。公司内部的验收负责人使用 `project:confirm`，同时必须能够访问对应项目。

本次不批量覆盖手工角色配置。当前“外部公司”已由用户配置为六项资料协作权限，保留原样；不会为了支持申请能力而自动授予提交权限。

## 升级现有数据库

在停写并备份后，用新版程序执行 `dotnet Yf.Api.dll --migrate-database`，再启动新版。升级到 .NET schema version 3，不需要 Rust。

迁移将历史 `PENDING_CONFIRMATION` 且确认方为 `SUPPLIER` 的申请转交内部验收，并处理这些申请仍指向供应商的旧待发通知。已完成项目与既有历史不改写；不重置账号、密码、角色、SMTP 和系统参数。迁移支持重复执行，启动只校验、不自动升级。
