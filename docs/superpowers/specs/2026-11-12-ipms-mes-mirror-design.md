# IPMS（MES 监控）数据镜像设计

日期：2026-11-12　状态：已实现（Task 1 到 5），待用专用账号联调

## 目的与背景

外协清单需要工令的客户、机型、交期等 IPMS 数据（见 `server_dotnet/docs/外协清单契约-2026-11-09.md`），但真实 IPMS 接口一直未定，目前只有 `FakeIpmsClient`。

用户确认：IPMS 的数据来源就是「迅得二期」的 **MES监控** 页面。本设计把该页面背后的数据定期抓取到本系统数据库，作为镜像表保存，再让外协清单从镜像表读取。

## 已验证的事实（2026-11-12 实测，只读）

- 前端 `http://183.238.37.108:6008`，后端 Java 微服务在 **6001 端口**，全部 HTTP 明文。
- 登入：`POST :6001/xyj-admin/r/login`，JSON：`account`、`password`、`usertype:0`、`captcha`（空）、`yzmState:0`、`suffix`。当前不需要验证码。请求头带 `captchaKey`，其必要性未验证。
- 认证凭证是请求头 **`token`**，不是 Cookie。凭证只存在浏览器分页内，关闭分页即失效或丢失。
- 数据：`POST :6001/xyj-twxd-mes/r/xdSalesOrder/queryByMesMonitor`。
  - 请求：`pageBean{page,pageSize,showTotal,summary}`、`querys[]`（页面默认 `productionStatus IN [1,2,0]` 与 `outMachineStatus IN [0]`）、`sorter`、`params` 等。
  - 响应：`{code:200, msg, data:{rows, total, page, pageSize, ...}}`；`total` 实测为字符串 `"1778"`。每行约 142 个字段，含 `workOrder`、`customerName`、`deviceModels`、`deliveryDate`、各阶段计划/实际日期与负责人。
- 性能：20 条约 40 秒；200 条约 50.5 秒（732 KB）；耗时以固定开销为主，不随条数线性增长。
- 2000 条一页：测试时浏览器分页卡死，未得结果；用户决定不采用。
- 未验证：登入响应结构、token 有效期与过期时的响应、`captchaKey` 是否必要、同账号并发登入是否互踢、`querys` 能否用于过滤（如按工令）、`sorter` 是否保证翻页稳定。

## 目标

1. 每天定时把 MES 监控全部数据抓到本库镜像表。
2. 每轮先抓满再整表替换；失败时保留上一轮数据。
3. 抓取全部在后台执行，不在用户请求或业务事务中调用外部系统。
4. 登入凭证与 token 只存在服务器内存和外部配置文件，不入库、不写日志。

## 非目标与反目标

- 不改动 MES 系统的任何数据；只调用读取接口。
- 不做实时同步、不对 MES 加压（不并发、不高频）。
- 不在本阶段把镜像字段映射成外协契约字段（见「待定」）。
- 反目标：因为抓取失败导致外协清单拿到空数据；因为频繁登入把 MES 里其他人（或专用账号本身）踢下线。

## 约束

- 沿用 .NET 8、EF Core、MySQL，迁移走 `dotnet ef migrations add`，并按 CLAUDE.md 更新 `SchemaShapeTests.ExpectedMigrations`、`MigrationRoundTripTests.Latest`。
- 现有 `IIpmsClient.LookupAsync(workOrderNos)` 契约不变。
- 配置放 `App:Ipms`，生产只读外部配置文件；账号、密码为秘密，不得出现在日志、审计、异常消息中。
- 测试不得连真实 MES；用本地假服务器（`HttpMessageHandler` 或 TestHost 内的假端点）。

## 方案

**A（推荐）：抓取进本地镜像，`IIpmsClient` 读镜像。**
后台服务按日抓取到暂存表，成功后事务内整表替换；新增 `MesMirrorIpmsClient : IIpmsClient`，`LookupAsync` 直接查本库。外协的汇入预览、同步、校验完全不碰外部系统，也不受 MES 慢（40 到 50 秒）影响。代价是数据最多滞后一天，与契约「每天同步」一致。

**B：`IIpmsClient` 实时调用 MES。**
每次汇入预览或同步都远程查询。每次查询至少约 40 秒，用户请求会卡死，且要处理分页与过期。与契约「外部调用不放在用户请求中」冲突，否决。

**C：浏览器自动化读页面。**
需要无头浏览器、脆弱、更慢。仅在接口被封时作为备选，否决。

选择 A。

## 设计（方案 A）

### 抓取流程（`MesMirrorSyncService`，托管服务）

1. 到点（默认 03:00，业务时间 UTC+8，每个业务日一次；`App:WorkerEnabled=false` 或未配置时不运行）。调度与租约方式同现有 `OutsourceIpmsSyncService`。
2. 登入取得 token，保存在内存。
3. 顺序翻页，`pageSize=100`（用户 2026-11-12 指定；已实测 200 可行，100 未实测），页与页之间可配置间隔（默认 2 秒）。每页超时 3 分钟，每页失败重试 2 次（含必要时重新登入）。
4. 每页写入暂存表（带本轮批次号）。
5. 抓满标准：累计去重后的行数等于首页 `total`，且工令无重复缺漏。不满足则整轮失败，不替换。若 `total` 与上一轮相比骤降（阈值待定，如少于上一轮 50%），也视为异常，不替换。
6. 校验通过，在一个事务内：删除正式表全部行、从暂存表插入、写入同步状态（成功时间、笔数、耗时）；随后清理暂存表。
7. 记录审计与同步状态：开始/结束时间、每页耗时、笔数、失败原因（不含凭证）。

### 会话保持

不做「保持会话」。每轮自己登入；遇到未登入或 token 无效的响应，重新登入一次并重试该页；再失败则整轮失败。全程只有一个抓取任务，避免同账号并发登入。

### 存储

- 镜像表保存：工令（唯一键）、批次号、抓取时间、整行原始 JSON，以及一组后续映射需要的、已确认的列（如工令、客户、机型、交期）。
- 原始 JSON 保留的理由：字段多（约 142 个）、MES 字段含义可能调整，后续映射可以重新计算而不必重抓。
- 暂存表与正式表同结构，或用批次号区分同一张表（实现时选择，倾向后者的「写入批次后原子切换」不适用于 MySQL 5.7 的整表替换，建议用独立暂存表）。

### 与外协清单的衔接

`MesMirrorIpmsClient.LookupAsync` 从镜像表按工令读取并映射为 `IpmsWorkOrder`。`App:Ipms:Mode` 新增 `MesMirror`，`IpmsOptions` 增加 MES 地址、账号、密码、间隔等设置，`Validate` 同步更新。

### 配置（`App:Ipms`，外部配置文件）

`Mode=MesMirror`、`MesBaseUrl`、`MesAccount`、`MesPassword`、`SyncTime`、`PageSize=100`、`PageDelaySeconds`、`PageTimeoutSeconds=180`。

### 安全与运维

- 使用**专用只读账号**；账号密码只在服务器配置文件中。日志与异常消息过滤凭证；`Authorization` 类头部不落盘。
- MES 为明文 HTTP，需在部署文档注明风险，并要求专用账号权限最小。
- 起始需实测并记录整轮耗时（预计 18 页；若每页约 45 到 50 秒，约 14 到 15 分钟，需实测）与笔数，写入验证记录。
- 抓取要避开白天高峰，默认凌晨。

### 测试

- 假 MES 服务：登入、分页、`total` 字符串、过期返回未登入、慢响应、返回异常 JSON。
- 覆盖：抓满替换、失败保留旧数据、笔数骤降拒绝替换、重新登入重试、凭证不进日志、未配置时不运行、并发租约。
- 不连真实 MES；真实联调由用户在服务器上手动触发一次，并记录结果。

## 对外协契约的连带变更（用户已确认；2026-11-13 已实现）

1. 汇入模板列改为：外发日期、工令、外发厂商、**外发类型**（生管填写）。
2. 外发类型不再属于 IPMS 字段：不由同步维护。匯入之后采购可以修改外发类型（用户确认），单笔和批量编辑都支持；与修改外发厂商一样，保存时校验类型与厂商的对应关系，不符则拒绝保存。采购同时改厂商和类型时，按两者的新值一起校验。已发送的记录改类型后转为「有变更待通知」，变更进入变更履历。
3. 防呆在汇入和修改时校验：类型须在启用的字典中，且该厂商在该类型的可用厂商内；不符则该行报错，不能汇入。
4. 删除契约中「同步后类型改变导致不符」「IPMS 带回字典中没有的类型」两种标记及相关发送阻止（类型只能是合法值，因此不再出现）。
5. 「数量」来自 MES 的「数量」列，类型与数量以外的 IPMS 字段映射见「待定」。
6. `IpmsWorkOrder.OutsourceTypeCode` 不再由 IPMS 提供；`outsource_items.type_code` 的来源改为汇入/编辑，不再被同步覆盖。需要迁移检查：现有数据（开发阶段）不保证兼容，按项目约定重建即可。

## 手动抓取（2026-11-12 追加）

用户要求 IPMS 同步部分支持：抓指定某一页、指定每页条数、手动触发、中途停止，并且停止后要二次确认是否更新库。已确认的决定：

- 手动「抓指定页」：指定页码与每页条数，只抓这一页；结果先停在暂存表，界面显示这一页的工令，由用户选择「放弃」（镜像不变）或「合并写入」（按工令更新或新增，不删除镜像里的其他工令）。
- 手动「抓取全部」：可指定每页条数；运行中可「停止」。停止后，已抓到的部分先留在暂存表，二次确认「放弃」（保留旧镜像）或「合并已抓部分」（更新或新增已抓到的工令，不删除没抓到的）。

我替用户做的决定（请确认或否决）：
1. 手动「抓取全部」若不中断地抓完并通过校验，与定时抓取一样直接整表替换，不再确认（确认只出现在「停止」和「抓指定页」之后）。
2. 同一时间只允许一个抓取任务（定时或手动）；等待确认的结果占用租约，直到用户确认、放弃或租约过期（60 分钟），过期后视为放弃，下次抓取开始时会清空暂存表。
3. 只有 `outsource:settings` 权限可以手动抓取、停止、确认；界面放在外协设定页的「IPMS 同步」分页。
4. 合并不改动「最近一次完整成功时间」，只更新镜像笔数基准（用于下次的笔数骤降保护），并写审计。
5. 页码从 1 起，每页条数 1 到 200（与配置上限一致）。

## MES 地址可在页面配置、测试连接（2026-11-12 追加）

用户要求 MES 地址能在页面上更换（现在测外网，之后可能换内网），并问 token 是否需要手动登入获取。

- token 由程序用配置文件里的账号密码自动登入获取，过期自动重登，不需要手动取。页面提供「测试连接」：用当前或待保存的地址全新登入并抓 1 条，只报告成功与否、总笔数、耗时，不写任何数据，也不显示 token。
- MES 地址保存在 `mes_mirror_state.base_url`（页面可改，留空恢复使用配置 `App:Ipms:MesBaseUrl`）。账号与密码仍只放外部配置文件，因为秘密不入库；换到内网若账号不同，需要改配置文件并重启。
- 改地址会让旧 token 失效并重新登入；运行中或等待确认时不允许改地址或测试，避免打断抓取或互相踢下线。
- 安全提示：有 `outsource:settings` 权限的人可以让服务器向任意 http/https 地址发送登入请求（带专用账号的密码）。因此地址保存写审计，并限制为 http/https、不含内嵌账号密码；该权限只应授予可信的采购人员。

## 待定（需要用户或实测）

- 专用账号及其权限；token 有效期与过期响应；`captchaKey` 是否必要。
- MES 字段到 `IpmsWorkOrder` 的映射：客户、机型、机构课别、机构/电控执行人、工令下发、BOM 时间、发图、交期、结案。
  - **数量**：对应 MES 监控页的「数量」列（用户 2026-11-12 确认）；JSON 字段名暂估为 `deviceNum`，需对照页面该列核实。
  - **外发类型**：用户确认**不来自 MES，改为人员填写**。这改变外协契约：类型不再由 IPMS 带出，同步不再改类型，「同步后类型与厂商不符」「未知类型」两种情况随之消失，类型与厂商的防呆改为在填写时校验。用户确认：**生管在汇入时与厂商一起填**。
  - **结案**暂可能对应 `productionStatus` 或 `outMachineStatus`，需确认。
- `querys` 能否在服务端按工令过滤（可用于外协汇入时的补查）。
- 当前页面筛选只含「未分配、已分配、任务中」与未出机，是否需要抓全部状态（包括任务完成），取决于外协要不要已完工的工令。
- 镜像表数据的保留与访问权限（含客户名称等业务数据）。
